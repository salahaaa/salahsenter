# قاعدة حوكمة التطوير والتغيير

> **لا إضافة بدون حساب التوسع، ولا إضافة بدون حساب الصيانة.**

هذه قاعدة إلزامية لأي ميزة أو تعديل أو migration أو تكامل جديد في المنصة.

## بوابة ما قبل التنفيذ

لا يبدأ تنفيذ التغيير قبل توثيق النقاط التالية:

1. **هدف واضح ونطاق محدود**
   - ما المشكلة التي يحلها؟
   - ما الذي لا يشمله التغيير؟

2. **تحليل التوسع Scalability**
   - أثره على قاعدة البيانات، الفهارس، حجم البيانات، وعدد الاستعلامات.
   - أثره على API، الكاش، الـ queue، التخزين والاتصال الخارجي.
   - سلوك النظام عند زيادة المستخدمين والمتاجر والطلبات والوسائط.
   - تجنب تصميم يحتاج إعادة بناء عند النمو.

3. **خطة الصيانة Maintenance Plan**
   - مالك واضح للمكون ومسار تشغيله.
   - logging ومؤشرات مراقبة وalerts مناسبة.
   - آلية retry وdead-letter حيث توجد عمليات غير متزامنة.
   - توثيق الإعدادات والأسرار والـ runbook.
   - سياسة تحديث dependencies وmigration وrollback.

4. **السلامة والتوافق**
   - التوافق مع البيانات والأدوار والـ APIs القائمة.
   - migration تدريجي وآمن عند الحاجة.
   - عدم كسر العملاء أو التكاملات الحالية.
   - مراجعة الأمن والعزل والصلاحيات وخصوصية البيانات.

5. **الجودة قبل الدمج**
   - unit/integration tests مناسبة.
   - فحص lint وtypecheck وmigration/security checks.
   - اختبار أداء أو staging عند تغييرات المسار الحرج.
   - خطة تراجع واضحة عند فشل النشر أو التكامل.

## الحد الأدنى في تقرير كل حزمة

أي تقرير تطوير جديد يجب أن يذكر صراحة:

```text
- أثر التوسع المتوقع
- خطة الصيانة والمراقبة
- migrations أو تغييرات البيانات
- استراتيجية التوافق والـ rollback
- الاختبارات المنفذة
- القيود أو الاعتمادات الخارجية المتبقية
```

## قرارات مرفوضة

لا تقبل أي إضافة إذا كانت:

- تربط المكون مباشرة بقاعدة بيانات نظام خارجي.
- تخزن أسراراً أو بيانات ضخمة داخل source code أو قاعدة بيانات بلا سياسة تخزين.
- تضيف استعلامات غير مفهرسة لمسارات عالية الاستخدام.
- تعتمد على عملية يدوية بلا مراقبة أو retry أو سجل تدقيق عند الحاجة.
- تغير schema أو API عام بلا migration وتوافق وrollback.
- تنفذ فقط لإكمال واجهة دون حماية API أو صلاحيات أو اختبارات.
