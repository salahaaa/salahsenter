# تقرير تطوير إدارة الموظفين والصلاحيات الدقيقة

**التاريخ:** 2026-07-13  
**النطاق:** لوحة الأدمن ولوحة التاجر — مشروع صلاح سنتر / Mall OS  
**الحالة:** مكتمل على مستوى البنية والواجهات الأساسية، مع ضوابط تشغيلية موضحة في قسم الحدود.

---

## 1) ما تم تنفيذه

### فصل واضح بين الشاشتين

تم فصل إدارة بيانات الموظف عن إدارة صلاحياته:

| المجال | لوحة الأدمن | لوحة التاجر |
|---|---|---|
| إدارة الموظفين | `/admin/employees` | `/merchant/employees` |
| إدارة الصلاحيات | `/admin/permissions-management` | `/merchant/permissions-management` |
| المسارات المختصرة الذكية | `/employees` | `/permissions-management` |

المسارات المختصرة تحدد لوحة المستخدم حسب صلاحياته ونطاقه.

### بيانات الموظف

شاشة الموظفين تدعم:

- الاسم الكامل، الهاتف، البريد الإلكتروني.
- **اسم مستخدم فريد** (تخزينه بصيغة lowercase) ويمكن تسجيل الدخول به.
- كلمة مرور قوية إلزامية عند الإنشاء، مع `mustChangePassword=true`.
- صورة موظف عبر رابط أو رفع ملف باستخدام خدمة الوسائط الحالية.
- الرقم الوظيفي/كود الموظف، المسمى الوظيفي، القسم للأدمن، الهوية، العنوان، الملاحظات وتاريخ التوظيف.
- الحالات الثلاث المطلوبة فقط في واجهة الموظفين:
  - `ACTIVE`
  - `SUSPENDED`
  - `INACTIVE`

> تم الإبقاء على القيم التاريخية `pending` و`deleted` في enum القديم لتوافق السجلات السابقة، لكنها ليست حالات اختيار للموظف الجديد.

### بدون صلاحيات افتراضية

عند إنشاء موظف منصة أو متجر:

1. ينشأ المستخدم وملف الموظف.
2. ينشأ **دور هوية تقني فارغ** فقط لربط الموظف بنطاق المنصة/المتجر.
3. لا يضاف أي صف في `role_permissions` ولا `user_permissions`.
4. لا يمنح `admin.access` أو `merchant.access` تلقائياً.

وبالتالي لا تصبح أي شاشة تشغيلية متاحة قبل أن يفتح المسؤول شاشة إدارة الصلاحيات ويمنح الوصول صراحةً.

### الإيقاف الفوري

- `SUSPENDED` و`INACTIVE` يمنعان الدخول لأن التحقق من الحالة يتم في كل طلب محمي.
- عند تغيير الحالة إلى غير نشطة أو إلغاء التفعيل، يتم إلغاء جلسات المستخدم الحالية في قاعدة البيانات فوراً.
- الإلغاء لا يحذف ملف الموظف أو الدور أو تجاوزات الصلاحية؛ يمكن إعادة التفعيل واسترجاع الصلاحيات السابقة.

## 2) نموذج RBAC + Permission Overrides

تم توسيع نموذج البيانات ليغطي:

```text
Users
Roles
Permissions
RolePermissions
UserRoles
UserPermissions   ← جديد: grant / deny لكل مستخدم
```

### جدول `user_permissions`

Migration جديدة:

```text
drizzle/0057_employee_management_granular_permissions.sql
```

الحقول المهمة:

```text
user_id
permission_id
store_id          -- NULL لصلاحيات المنصة، وإجباري منطقياً لصلاحيات المتجر
effect            -- grant | deny
reason
created_by
created_at
updated_at
```

توجد فهارس فريدة منفصلة لمنع التكرار في نطاق المنصة وفي نطاق كل متجر.

### أولوية القرار

قرار الصلاحية الدقيق يتم بهذا الترتيب:

```text
Super Admin
↓
Direct DENY            (يمنع حتى لو الدور يسمح)
↓
Direct GRANT           (يضيف صلاحية للموظف)
↓
RolePermissions        (الصلاحيات الموروثة من الدور)
↓
Deny by default
```

واجهة إدارة الصلاحيات تعرض لكل عملية ثلاث حالات:

- **وراثة الدور:** لا يوجد تجاوز فردي؛ يسمح أو يمنع حسب الدور.
- **منح مباشر:** يمنح العملية للموظف نفسه.
- **سحب / منع:** يلغي العملية حتى عند وجودها في الدور.

## 3) كتالوج الصلاحيات الدقيقة

الملف المركزي:

```text
lib/permissions/catalog.ts
```

تمت إضافة **86 صلاحية دقيقة** قابلة للعرض والإسناد، مع فصل نطاق المنصة عن نطاق المتجر في:

```text
lib/permission-scopes.ts
```

### أمثلة لوحة الأدمن

- الإعلانات: عرض، إنشاء، اعتماد، رفض، تعديل، حذف، تغيير انتهاء، تمييز، إيقاف، استعادة.
- المنتجات: عرض، إنشاء، تعديل، حذف، تعديل جماعي، تغيير سعر، إدارة مخزون، استعادة.
- المتاجر: عرض، اعتماد، إيقاف، تفعيل، تعديل، حذف.
- الطلبات: عرض، تعديل، تغيير الحالة، إلغاء، استرداد، إغلاق.
- العملاء: عرض، تعديل، إيقاف، حذف.
- الموظفون: عرض، إنشاء، تعديل، إلغاء تفعيل، إدارة صلاحيات.
- المالية: عرض/تصدير تقارير، تسويات، عمولات، سحوبات.
- البنوك والمحافظ: إضافة، تعديل، إيقاف، حذف.
- النظام: عرض/تعديل إعدادات، تكاملات، ERP، مركز الأمان.

### أمثلة لوحة التاجر

- المنتجات والمخزون والطلبات والعملاء.
- الموظفون والصلاحيات.
- الفروع والمالية والإعلانات والشحن والدفع.
- كود صلاحية المتجر يحمل بادئة `store.*`، مثل:

```text
store.products.view
store.products.create
store.inventory.manage
store.orders.status.change
store.employees.permissions.manage
```

لا يمكن تمرير صلاحية منصة إلى موظف متجر، ولا تظهر صلاحيات المتجر في مصفوفة موظفي المنصة.

## 4) واجهات ودعم الأدوار المخصصة

### الإدارة

- إدارة الموظفين مستقلة عن المصفوفة.
- شاشة الصلاحيات تختار الموظف من القائمة ثم تعرض الصلاحيات مجمعة حسب الإدارة.
- يمكن اختيار دور موروث اختياري، ثم إضافة تجاوزات `grant/deny` للموظف.
- لوحة الأدوار الحالية `/admin/roles` تستقبل صلاحيات المنصة الدقيقة الجديدة.

### التاجر

- أنشئ موظف المبيعات أو المخزون أو الطلبات أو خدمة العملاء بلا وصول افتراضي.
- من `/merchant/permissions-management` يمكن إنشاء دور متجر مخصص بصلاحيات مختارة ثم تعيينه للموظف.
- يمكن تعديل أي دور موروث بتجاوز فردي دون إنشاء دور جديد.
- جميع تعيينات المتجر تشمل `store_id`، والتحقق من `hasStoreAccess` يبقي الوصول في نطاق المتجر فقط.

## 5) التدقيق والأمن

تمت إضافة سجلات Audit للتالي مع الممثل والقيم قبل/بعد:

- إنشاء موظف منصة أو متجر.
- تعديل بيانات الموظف.
- تغيير الحالة، الإيقاف المؤقت وإلغاء التفعيل.
- تعيين/تغيير الدور الموروث.
- منح مباشر، سحب مباشر، وإزالة Override للصلاحيات.

كيانات التدقيق تشمل مثلاً:

```text
employee.platform.create
employee.platform.update
employee.platform.status_change
employee.platform.permission_overrides
employee.store.create
employee.store.status_change
employee.store.permission_overrides
```

كما أن معقم سجلات التدقيق يخفي كلمات المرور والـ hashes والأسرار.

## 6) ربط تشغيلي أولي للصلاحيات الدقيقة

بالإضافة إلى واجهات الإدارة، تم ربط بعض واجهات المتجر التشغيلية بالصلاحيات الجديدة مع الحفاظ على fallback متوافق للأدوار القديمة:

| العملية | الصلاحية الدقيقة الجديدة |
|---|---|
| عرض منتجات المتجر | `store.products.view` |
| إنشاء منتج | `store.products.create` |
| تعديل منتج | `store.products.edit` |
| حذف منتج | `store.products.delete` |
| تغيير أسعار جماعي | `store.products.prices.change` |
| عرض المخزون | `store.inventory.view` |
| تعديل المخزون | `store.inventory.manage` |
| تغيير حالة طلب | `store.orders.status.change` |
| عرض حملات المتجر | `store.ads.view` |
| إدارة حملات المتجر | `store.ads.manage` |
| عرض مالية المتجر | `store.finance.view` |

هذا الربط يضمن أن الدور القديم الذي يستخدم الصلاحيات العامة يستمر بالعمل أثناء الانتقال، بينما الموظفون الجدد يستطيعون استخدام الصلاحيات الدقيقة في العمليات المذكورة.

## 8) ما يلزم قبل النشر الفعلي

لم يتم تطبيق migration على قاعدة إنتاج أو نشر الموقع؛ التنفيذ محلي فقط.

قبل الإتاحة التشغيلية:

1. تطبيق migration `0057_employee_management_granular_permissions.sql` عبر مسار CI المعتمد.
2. إنشاء أدوار مخصصة وتوزيع الصلاحيات الدقيقة للمشرفين/التجار التجريبيين.
3. تنفيذ اختبار HTTP/قاعدة بيانات حقيقي يتضمن:
   - إنشاء موظف بلا صلاحيات.
   - التأكد من رفض فتح عملية محمية.
   - منح صلاحية محددة فقط.
   - اختبار `deny` فوق الدور.
   - تعليق الحساب والتحقق من إبطال الجلسة فوراً.
   - اختبار موظف متجرين مختلفين ضد IDOR.
4. استكمال تحويل بقية APIs التاريخية التي ما زالت تستخدم مفاتيح عامة مثل `products.manage` أو `ads.manage` إلى مفاتيح عملية دقيقة؛ تم الإبقاء على fallback متوافق عمداً لمنع تعطل الأدوار الموجودة أثناء هذا التحول.

### حد صريح

المصفوفة والـ APIs الخاصة بالموظفين مكتملة، كما رُبطت العمليات التجارية الأساسية المذكورة أعلاه. لكن لا يصح الادعاء بأن **كل** API قديم في المشروع أصبح دقيقاً على مستوى الزر؛ المشروع يحتوي مسارات تاريخية إضافية تستخدم صلاحيات module عامة وتحتاج حزمة تحويل متابعة، مع اختبارات E2E لكل route قبل إزالة fallback التوافقي.
