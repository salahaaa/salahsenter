# تصميم التغيير: حسابات QA متعددة ومركز تصفية ما قبل الإطلاق

**التاريخ:** 2026-07-16  
**الحالة:** منفذ محلياً — لا تطبق عملية التصفية أو migrations على Staging/Production قبل اختبارها واعتمادها.

## الأهداف

1. تمكين أكثر من موظف من اختبار الأدوار بالتوازي:
   ```text
   2 أدمن QA
   2 تاجر QA
   2 عميل QA
   ```
2. منع حسابات QA، حتى التي تملك `super_admin`، من الدخول لمركز التحكم الحساس.
3. توفير مركز واحد للعمليات شديدة الحساسية.
4. إنشاء تصفية مقصودة لبيانات ما قبل الإطلاق، مع مسار آمن لإنشاء مالكي المنصة بعد التصفية.
5. توفير حسابي مالك مستقلين لاستعادة السيطرة بعد تسرب أحد البريدين.

## حسابات QA

- ينشئ `npm run test:fixtures` ستة حسابات في Local/Staging فقط.
- يمنع السكربت تنفيذه عند Production.
- تحتاج كل الحسابات إلى بريد وكلمة مرور مختلفين.
- تنشأ لكل تاجر QA متجر وبيانات كتالوج ومخزون ودفع وشحن مناسبة للتجارب.
- الحقل `users.is_test_account=true` هو مصدر الحقيقة لمنع QA من العمليات الحساسة.

## مركز التحكم الحساس

المسار:

```text
/admin/sensitive-control
```

الضوابط:

- `super_admin` غير تجريبي فقط.
- كلمة مرور حساسة مستقلة عن كلمة مرور دخول الأدمن.
- تحفظ password hash فقط، ولا تحفظ كلمة المرور كنص.
- unlock session في HttpOnly cookie قصيرة العمر (10 دقائق).
- audit للعمليات الحساسة.
- لا MFA إلزامية ولا موافقة ثانية إجبارية.

العمليات:

```text
قفل التجارة/التسجيل/الرفع العام وإعادة فتحها
تعليق أو إغلاق متجر
إعداد/استبدال حسابي المالك
تصفية بيانات ما قبل الإطلاق
```

## تصفية ما قبل الإطلاق

### ما يحذف

```text
المستخدمون والتجار والمتاجر والفروع والموظفون
المنتجات والمتغيرات والمخزون والطلبات
العقود وبيانات التطبيقات التشغيلية
العروض والإعلانات والفوترة المرتبطة بها
الأخبار والبانرات والمحتوى اليدوي
الجلسات والإشعارات وسجلات الاستخدام اليدوي
الإعدادات ذات نطاق store:* وuser:*
```

### ما يبقى

```text
الأدوار والصلاحيات وقوالبها
Master Governance وإعدادات الهوية والحماية
الجغرافيا والأجنحة والكتالوج المرجعي
قوالب العقود والإعدادات المرجعية
migrations وjournal
```

### حماية التنفيذ

```text
1. جلسة تحكم حساسة مفتوحة.
2. تحذير واضح بالأثر.
3. إدخال كلمة المرور الحساسة ثلاث مرات.
4. transaction واحدة؛ أي فشل يعيد كل العملية.
5. قفل المنصة العامة أولاً.
6. تذكرة Bootstrap HttpOnly لمرة واحدة لمدة 15 دقيقة.
```

## ما بعد التصفية

```text
لا يوجد حساب يستطيع الدخول
→ المتصفح الذي نفذ التصفية فقط يحمل bootstrap ticket
→ /bootstrap-owner
→ إنشاء مالك 1 ومالك 2
→ كلاهما super_admin مستقل
→ تسجيل الدخول بأحدهما
→ تهيئة كلمة مرور مركز التحكم الحساس من جديد
→ مراجعة القفل ثم إعادة فتح المنصة يدوياً
```

## استبدال حساب مسرب

```text
الدخول بحساب المالك الآخر
→ فتح جلسة حساسة
→ إعداد/استبدال slot المالك المسرب
→ إلغاء جلسات الحساب القديم
→ تعليق الحساب القديم
→ إنشاء المالك البديل بدور super_admin
```

## التوافق والقيود

- التصفية لا تمس migrations أو إعدادات الأدوار المرجعية.
- `TRUNCATE/DELETE` يعمل ضمن transaction، لكن يحتاج اختبار PostgreSQL حقيقي قبل Production.
- لا تنفذ التصفية على بيئة إطلاق حقيقية قبل backup واستعادة Staging ناجحة.
- لا يحذف المركز متجرًا فرديًا تلقائياً؛ يغلقه أو يعلقه. الحذف الشامل المقصود يتم من تصفية ما قبل الإطلاق لتجنب كسر العقود والسجل المالي.

## اختبارات Staging المطلوبة

1. تشغيل fixtures والتحقق من الحسابات الستة والمتجرين.
2. التأكد أن أدمن QA يرى لوحة الأدمن لكنه لا يرى أو يدخل مركز التحكم الحساس.
3. تهيئة كلمة المرور الحساسة بحساب غير تجريبي.
4. إعداد المالك الثاني وتسجيل الدخول به.
5. اختبار قفل وإعادة فتح المنصة العامة.
6. إجراء purge على قاعدة Staging مخصصة فقط والتحقق من retention list.
7. استخدام bootstrap ticket وإنشاء مالكي المنصة.
8. التحقق من منع استخدام ticket مرة ثانية أو بعد انتهائه.
