# تصميم التغيير: ربط قطاع طلب المتجر بقوالب التجهيز ونوع منتجات البداية

**التاريخ:** 2026-07-16  
**الحالة:** تم استبدال اختيار القطاع المستقل لاحقاً بقرار الجناح كقطاع واحد؛ راجع `WING_AS_SINGLE_ACTIVITY_SECTOR_CHANGE_DESIGN_2026-07-16_AR.md`. غير مطبق على Staging أو Production.

## القرار

1. يختار التاجر في طلب فتح المتجر **قطاع النشاط لإعداد الكتالوج** من قائمة القوالب النظامية والقطاعات النشطة التي يديرها الأدمن.
2. يحتفظ الطلب بمفتاح القالب (`activity_template_key`) وينقل المفتاح ذاته إلى المتجر عند الاعتماد النهائي.
3. عندما يفتح التاجر شاشة القوالب، لا تظهر له إلا القالب/القطاع الذي اختاره في الطلب. يفرض الـ API القيد نفسه؛ لذلك لا يمكن تجاوزه بإرسال مفتاح قالب آخر من المتصفح.
4. عند طلب منتجات البداية الاختيارية، يحدد التاجر لكل منتج: 
   - `ONLINE_SALES`: للبيع الإلكتروني عند نشره لاحقاً؛ السلة والشراء يعملان وفق السياسات القائمة.
   - `SHOWCASE_ONLY`: للعرض والتواصل فقط؛ يمنع النظام السلة والشراء عند نشره لاحقاً.
5. منتجات البداية تبقى دائماً `draft`، بسعر `0` ومخزون `0`، ولا تنشر ولا تنشئ فاتورة أو قيداً مالياً.

## الدافع التجاري وتجربة المستخدم

القطاع ليس حكماً مالياً ولا يعني أن كل منتجاته تباع بالطريقة نفسها. فقد يجمع متجر الذهب مثلاً بين إكسسوارات قابلة للبيع الإلكتروني وذهب يحتاج الحضور. لذلك حُفظ القرار على **مستوى كل منتج بداية** بدلاً من افتراض نوع بيع واحد للقطاع كله.

لا يظل التاجر أمام كل القطاعات بعد تحديد نشاطه في الطلب؛ يرى القطاع المتفق عليه فقط، ثم يراجع معاينة التصنيفات والوحدات والخصائص والمنتجات قبل التطبيق.

## النطاق

- نموذج طلب المتجر الأول وطلب النشاط المستقل.
- إعادة إرسال طلب طلبت الإدارة تعديله، بما في ذلك الطلبات القديمة التي لا تحمل قطاعاً محفوظاً.
- اعتماد الطلب النهائي ونسخ القطاع إلى سجل المتجر.
- API وشاشة القوالب للتاجر.
- إنشاء منتجات البداية الاختيارية.

## تصميم البيانات والتوافق

Migration `0080_onboarding_activity_template_scope` تضيف حقلي nullable:

- `merchant_applications.activity_template_key`
- `stores.activity_template_key`

مع فهارس مستقلة للبحث والتدقيق. الحقول nullable عن قصد:

- لا يعاد تصنيف متجر أو طلب قديم تلقائياً.
- المتاجر القديمة تستمر في عرض القائمة القديمة إلى أن يضاف لها مسار تعيين/تحويل مدقق منفصل.
- كل طلب جديد أو إعادة إرسال تتطلب اختيار قطاع نشط ومتحقق منه على الخادم.

**Rollback:** موثق داخل SQL: إزالة الفهارس ثم الأعمدة فقط بعد نشر كود لا يقرأها. لا توجد عملية rollback آلية في بيئة حية.

## حدود API والتحقق

- `POST /api/merchant-applications` و`PATCH /api/merchant-applications/:id` يتحققان أن مفتاح القطاع موجود ضمن القوالب النظامية أو الكتالوج الإداري النشط.
- `GET /api/merchant/activity-templates` يفلتر النتائج بمفتاح المتجر إن كان موجوداً.
- `POST /api/merchant/activity-templates` يرفض قالباً لا يطابق قطاع المتجر المحفوظ.
- `starterProductModes` مصفوفة محددة من `ONLINE_SALES` و`SHOWCASE_ONLY`، وتستخدم بحسب ترتيب منتجات بداية القالب.

## حساب التوسع (Scalability)

| عنصر | قرار التوسع |
|---|---|
| البيانات | مفتاح نصي قصير مفهرس؛ لا يكرر JSON القالب داخل كل متجر ولا يضيف جداول عالية النمو. |
| القراءة | قائمة القوالب تجمع قائمة نظامية ثابتة مع القطاعات الإدارية النشطة ثم ترشح في الذاكرة؛ حجمها محدود إدارياً. |
| الكتابة | اختيار واحد عند الطلب ونسخ واحد داخل transaction اعتماد المتجر؛ لا توجد كتابة جماعية. |
| منتجات البداية | الحد الحالي للكتالوج 50 منتجاً؛ إنشاؤها تسلسلي ومحدود، مع marker يمنع التكرار. |
| cache/queue/storage | لا cache أو queue أو ملفات جديدة. لا توجد صور أو OCR أو بيانات مالية. |
| مستقبل التوسع | إن احتاجت المنصة تجميد نسخة القالب لكل متجر أو تغيير قطاع متجر قائم، ينفذ ذلك عبر assignment/version snapshot ومدقق مستقل، لا بتعديل المفتاح بصمت. |

## خطة الصيانة والمراقبة

- **المالك الوظيفي:** فريق إدارة الكتالوج/المنتجات.
- **المالك التقني:** فريق المنصة والتاجر.
- يسجل audit لتطبيق القالب، وتتضمن علامة منع التكرار نتيجة منتجات البداية وأنماطها المختارة.
- رسائل تشغيلية واضحة للحالات التالية: قطاع معطل أو غير متاح، محاولة تطبيق قطاع مختلف، وعدم وجود وحدة بيع للمتجر.
- لا توجد مهمة دورية أو queue أو DLQ؛ فإن أضيفت معالجة غير متزامنة للمنتجات لاحقاً يجب أن ترافقها retry/DLQ/runbook.
- يراجع الأدمن تعطيل قطاع بعناية: الطلبات الجديدة لا تستطيع اختياره، والمتجر المرتبط بقطاع إداري معطل لن يحصل على قالب قابل للتطبيق إلى أن يعاد تفعيله أو ينفذ مسار تحويل مدقق لاحقاً.

## الأمن والحوكمة

- لا يثق النظام بمفتاح القالب الوارد من الواجهة؛ يتحقق منه على الخادم.
- لا يسمح API تطبيق القوالب بتجاوز القطاع المحفوظ للمتجر.
- لا تعديل تلقائي لحالة النشر أو السعر أو المخزون أو السلة أو التدفقات المالية.
- `SHOWCASE_ONLY` يعتمد على حواجز السلة والطلب القائمة، لا على إخفاء زر واجهة فقط.
- لا أسرار أو تكاملات خارجية أو بيانات هوية إضافية في هذا التغيير.

## الاختبارات المطلوبة

1. اختبار وحدات: قصر القوالب على قطاع المتجر، والتوافق مع المتاجر القديمة، واختيار نوع منتج البداية.
2. Lint وTypecheck وVitest الكامل.
3. تحقق journal وDrizzle check.
4. فحص الحماية وفرق Git.
5. لاحقاً في Staging: تشغيل migration، تقديم طلب جديد، اعتماد المتجر، محاولة تطبيق مفتاح مختلف، ثم فحص منتج بداية من النوعين بعد نشر يدوي مضبوط.
