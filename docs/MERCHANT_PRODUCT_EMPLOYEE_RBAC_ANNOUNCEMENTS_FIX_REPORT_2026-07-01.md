# تقرير إصلاح تحكم التاجر بالمنتجات والموظفين والصلاحيات والإعلانات

التاريخ: 2026-07-01

## نطاق الفحص

تم فحص ومعالجة النقاط التالية:

1. تحكم التاجر الكامل بمنتجاته ومتغيراته، خصوصاً إضافة لون/خاصية بعد نشر المنتج.
2. أخطاء إضافة الموظفين في لوحة الأدمن ولوحة التاجر.
3. شاشة الصلاحيات RBAC وخلط صلاحيات الأدمن مع صلاحيات المتاجر.
4. مشكلة عدم ثبات رسالة النجاح بعد نشر الإعلان، مما قد يؤدي لتكرار الحفظ.

---

## 1. منتجات التاجر والمتغيرات

### المشكلة

كان مسار إنشاء المنتج يفرض على التاجر أشياء ليست دائماً مطلوبة:

- اختيار قسم/تصنيف.
- وجود متغيرات.
- اختيار وحدة لكل تركيبة.
- وجود قيمة متغير لكل تركيبة.

وهذا يخالف فكرة أن التاجر قد ينشر منتجاً بسيطاً الآن، ثم يعود لاحقاً لإضافة لون أو مقاس أو عبوة.

### ما تم تعديله

#### Backend

تم تعديل:

```txt
app/api/merchant/products/route.ts
app/api/merchant/products/[id]/route.ts
```

التغييرات:

- لم يعد اختيار التصنيف إجبارياً.
- لم تعد المتغيرات إجبارية عند إنشاء المنتج.
- لم تعد الوحدة إجبارية.
- لم تعد قيم الخصائص إجبارية.
- إذا أرسل التاجر قيماً لخصائص، يتم التحقق أنها تتبع متجره فقط.
- منع اختيار أكثر من قيمة لنفس الخاصية داخل نفس المتغير.
- عند عدم إرسال متغيرات يتم إنشاء متغير افتراضي بسيط.

#### Frontend

تم تعديل:

```txt
components/merchant/product-engine-form.tsx
components/merchant/product-edit-form.tsx
```

التغييرات:

- إزالة القيود الإجبارية من نموذج إضافة المنتج.
- السماح بإضافة منتج بسيط بدون تصنيف/وحدة/لون.
- تحسين شاشة تعديل المنتج حتى يستطيع التاجر إضافة/تغيير/إزالة خصائص المتغيرات بعد النشر.
- عند اختيار لون جديد لنفس المتغير يتم استبدال اللون القديم فقط، مع إبقاء المقاس/العبوة/الخصائص الأخرى.
- إضافة صندوق سريع داخل شاشة تعديل المنتج بعنوان:

```txt
إضافة خاصية أو قيمة ناقصة بسرعة
```

يسمح للتاجر بإضافة مثلاً:

```txt
اللون = أحمر
المقاس = XL
العبوة = كرتون
```

ثم العودة لاختيارها للمتغيرات.

### النتيجة

التاجر أصبح يستطيع:

- نشر منتج بسيط أولاً.
- العودة لاحقاً لإضافة لون أو مقاس أو عبوة.
- إضافة متغير جديد بعد النشر.
- تعديل متغير موجود وربطه بقيم خصائص جديدة.
- تعطيل متغير بدلاً من حذفه.

## 2. إضافة الموظفين في الأدمن والتاجر

### الفحص

تم فحص:

```txt
app/api/admin/employees/route.ts
app/api/admin/employees/[id]/route.ts
app/api/merchant/employees/route.ts
app/api/merchant/employees/[id]/route.ts
components/admin/platform-employee-management-panel.tsx
components/merchant/employee-management-panel.tsx
```

### السبب المرجح للأخطاء السابقة

قاعدة البيانات كانت قبل ذلك ناقصة migrations مهمة، خصوصاً:

```txt
platform_employees
store_employees.group_role_id
```

وقد تم تطبيق migrations المطلوبة سابقاً ضمن مسار الإنتاج الآمن.

### تحسين إضافي تم تنفيذه

في لوحة موظفي الأدمن كان اختيار مجموعة الصلاحيات داخل نافذة إدارة الصلاحيات لا يتم إرساله عند الحفظ.

تم تعديل:

```txt
components/admin/platform-employee-management-panel.tsx
```

ليتم حفظ:

```txt
groupRoleId
permissionCodes
```

معاً عند إدارة صلاحيات الموظف.

## 3. شاشة الصلاحيات RBAC

### المشكلة

كانت شاشة الصلاحيات تعرض الأدوار والصلاحيات بطريقة عامة وغير مفصولة بوضوح بين:

- صلاحيات المنصة / الأدمن.
- صلاحيات المتجر / التاجر.

كما كانت غير احترافية من ناحية تعديل بيانات الدور وتعطيله.

### ما تم تعديله

تم تعديل:

```txt
components/admin/role-management-panel.tsx
app/api/admin/rbac/roles/route.ts
app/api/admin/rbac/roles/[id]/route.ts
```

التغييرات:

- فصل الشاشة إلى تبويبين:

```txt
صلاحيات المنصة
صلاحيات المتاجر
```

- عند اختيار دور `system` تظهر فقط صلاحيات المنصة.
- عند اختيار دور `store` تظهر فقط صلاحيات المتجر.
- منع الخلط على مستوى الواجهة والـ API.
- إضافة تعديل اسم الدور والوصف.
- إضافة زر حفظ واضح.
- إضافة زر مسح صلاحيات الدور.
- إضافة زر تعطيل الدور للأدوار غير النظامية.
- منع تعطيل الدور النظامي مثل `super_admin`.
- عند إنشاء دور جديد لا يرث صلاحيات الدور المحدد حالياً بالخطأ؛ ينشأ بدون صلاحيات ثم يتم ضبطه يدوياً.

### النتيجة

أصبحت شاشة RBAC أكثر احترافية وأقل خطورة:

- لا خلط بين صلاحيات الأدمن والمتجر.
- تعديل بيانات الدور متاح.
- تعطيل/حذف الأدوار غير النظامية متاح.
- API نفسه يفلتر الصلاحيات حسب نطاق الدور، فلا يعتمد فقط على الواجهة.

## 4. مشكلة تكرار الإعلان بعد النشر

### المشكلة

بعد نشر الإعلان كانت رسالة النجاح/علامة الصح قد تختفي بعد تحديث الواجهة، فيضغط المستخدم حفظ مرة أخرى، مما يسبب تكرار الإعلان.

### ما تم تعديله

تم تعديل:

```txt
components/merchant/store-announcement-form.tsx
components/admin/marketplace-announcement-form.tsx
```

التغييرات:

- تثبيت رسالة النجاح باستخدام `sessionStorage` حتى لا تختفي مع `router.refresh()`.
- تعطيل زر الحفظ بعد نجاح العملية.
- تغيير نص الزر إلى:

```txt
تم الحفظ ✓
```

- إضافة زر واضح:

```txt
إضافة محتوى آخر
```

أو:

```txt
إعلان جديد
```

حتى لا يتم تكرار نفس الإعلان بدون قصد.

### النتيجة

- الواجهة تحدث البيانات.
- علامة النجاح لا تختفي مباشرة.
- زر الحفظ لا يسمح بتكرار نفس الإعلان.
- المستخدم يستطيع إنشاء إعلان جديد فقط عبر زر واضح.

## 6. ملاحظات مهمة

1. لم يتم تشغيل `db:seed`.
2. لم تتم إضافة migrations جديدة في هذا الإصلاح.
3. إصلاحات الموظفين استفادت من migrations التي تم تطبيقها سابقاً على قاعدة الإنتاج.
4. شاشة الصلاحيات أصبحت مفصولة منطقياً، لكن يمكن لاحقاً تطويرها إلى RBAC Builder كامل بواجهة drag/drop ونسخ قوالب صلاحيات.
