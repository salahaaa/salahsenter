# حزمة الاختبار الجماعي المتوازي في Staging — 23 يوليو 2026

## قرار التشغيل

هذه الحزمة **لا تنشر Production ولا تتصل بأي خدمة حقيقية**. الغرض منها إزالة الاعتماد على موظف أدمن واحد أو تاجر واحد، وتجهيز تجربة قبول بشرية متوازية على بيئة `Staging` فقط.

قاعدة العمل المعتمدة:

- لا تُشارك كلمات المرور أو جلسات الدخول بين أعضاء الفريق.
- حساب `super_admin` الأول في Staging يبقى لحساب قائد الاختبار/المالك فقط ولا يستخدمه الفريق يومياً.
- لكل فرد حسابه واسمه وسجل تدقيقه وصلاحياته اللازمة فقط.
- كل حساب تنشئه هذه الحزمة يحمل `is_test_account=true`، ولذلك لا يستطيع فتح مركز التحكم الحساس الخاص بالمالك حتى لو حاول الوصول إلى رابطه مباشرة.
- نموذج أموال العملاء ثابت: `merchant_collects`. العميل يدفع للتاجر مباشرة؛ فريق المالية يقرأ التقارير فقط ولا يتلقى صلاحية تسوية أموال العميل أو السحوبات.

### 2) إصلاح ضروري لعمل موظفي المتجر ذوي الصلاحيات الدقيقة

كانت بعض نقاط الحراسة تتعرف إلى موظف المتجر اعتماداً على الاسم القديم للدور (`store_employee`) فقط. أما نظام الصلاحيات الدقيق فينشئ أدوار مجموعات مخصصة لكل متجر، وهذا قد يمنع موظف الكتالوج أو التنفيذ من الوصول إلى واجهة التاجر رغم أن لديه دوراً مقيداً بالمتجر.

تم تعديل التحقق ليعتمد على:

```text
دور scope=store + storeId مطابق
```

بدلاً من اسم الدور الحرفي. لا يوسع ذلك نطاق الوصول:

- موظف المتجر الأول لا يصل إلى المتجر الثاني.
- حساب منصة بلا دور متجر لا يصبح تاجراً.
- ما زالت صلاحية العملية الدقيقة مطلوبة بعد اجتياز بوابة المتجر.

## بيانات Staging التجريبية الآمنة

ينشئ السكربت متجرين فقط بعلامة واضحة `STG-QA-*` وعبارة `STAGING TEST ONLY`.

- لا يعدل متجراً موجوداً لا يحمل علامة QA أو لا يملكه العضو المتوقع.
- ينشئ لكل متجر وسيلة COD وشحناً تجريبيين بلا تكلفة.
- ينشئ منتجاً **مسودة** فقط:

```text
status=draft
price=0
stock=0
```

لا يبدأ المنتج صالحاً للبيع. على موظفي الكتالوج أن يمروا بخطوات التسعير والمخزون والنشر بأنفسهم قبل سيناريو الشراء؛ وهذا يجعل اختبار دورة التاجر واقعياً بدلاً من تجاوزها ببيانات جاهزة.

### C. ترتيب Workflows الإلزامي

نفّذها من تبويب **Actions** بهذا الترتيب، ولا تتجاوز خطوة:

1. `CI` على النسخة المرفوعة — يجب أن ينجح، خصوصاً `npm run build` على Node 22.
2. `Apply Staging database migrations` واكتب:
   ```text
   APPLY_STAGING_MIGRATIONS
   ```
3. راجع نجاح migrations في السجل، ثم شغّل `Bootstrap first Staging platform administrator` واكتب:
   ```text
   BOOTSTRAP_FIRST_STAGING_ADMIN
   ```
   يفشل بأمان إذا كان يوجد بالفعل `super_admin` نشط؛ لا تحاول الالتفاف على ذلك.
4. شغّل `Provision isolated Staging test team` واكتب:
   ```text
   PROVISION_STAGING_TEST_TEAM
   ```
   واترك `reset_passwords=false` في أول تشغيل.
5. راجع ملخص Action: يجب أن يذكر 14 profile ومتجرين QA، من دون طباعة أي كلمة مرور.

خيار `reset_passwords=true` ليس إجراءً عادياً؛ لا يستخدم إلا عند فقدان كلمات المرور المؤقتة أو تدويرها. يعيد فرض تغيير كلمة المرور عند الدخول التالي على حسابات QA الموجودة.

## معايير إيقاف الاختبار والتصعيد

أوقف الجولة فوراً وصعّد لقائد الاختبار عند أي من الآتي:

- ظهور بيانات متجر أو عميل لعضو من نطاق آخر.
- إمكانية تنفيذ عملية رغم رفض API المتوقع.
- إنشاء طلب أو خصم مخزون مكرر بعد إعادة المحاولة.
- تسوية أو مسك أموال عميل داخل المنصة خلاف `merchant_collects`.
- رابط خاص بوثيقة قانونية يعمل بلا صلاحية.
- وصول أي حساب QA إلى التحكم الحساس أو إجراء Production.

لا يعالج العطل بتغيير البيانات يدوياً ثم وضع الحالة «ناجح»؛ توثق المشكلة، يعاد الاختبار من البداية بعد الإصلاح، وترتبط برقم الدليل.

## ما لم يتم تنفيذه فعلياً بعد

- لم يُرفع المصدر أو يُشغّل أي workflow في GitHub.
- لم تتصل هذه الحزمة بـ Neon أو Vercel أو R2 أو Redis أو خدمة البريد/SMS.
- لم تنفذ migrations، ولم ينشأ أي حساب أو متجر أو وثيقة حقيقي.
- لم تُجرَ تجربة Backup/Recovery أو R2 حقيقية؛ هذه تبقى بوابة تشغيلية مستقلة قبل Production.
- لا تزال GitHub Actions/Vercel على Node 22 هي بوابة build الفعلية؛ build المحلي في Arena ليس دليلاً كافياً بسبب حد الذاكرة.
