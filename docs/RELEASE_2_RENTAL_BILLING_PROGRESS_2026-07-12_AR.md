# Release 2 — عقود الإيجار، التحصيل، وسعات الباقات

**التاريخ:** 12 يوليو 2026
**الحالة:** الحزمة الأساسية وفرض سعات الباقات ورفع/مراجعة إثبات السداد مكتملة برمجيًا؛ Grace/Freeze والتحصيل المتقدم ما زالت تالية.

## الهدف

تحويل نموذج الربح إلى إيجار هجين للمتاجر والفروع والإضافات المدفوعة، دون خلطه بمدفوعات طلبات العملاء النقدية التي يستلمها التاجر.

## البيانات الجديدة

### `rental_addons`

كتالوج الإضافات المدفوعة:

```text
ERP connector
White-label domain
Extra branch
Advanced reports
Additional employee capacity
Advertising package
```

### `store_rental_agreements`

اتفاق مالي واحد لكل متجر:

```text
Store + Merchant + Legal Contract + Subscription Plan
Base Rent + Currency + Billing Cycle
Grace Days + Next Invoice + Status
```

### `store_rental_addon_assignments`

إضافات مفعلة لكل اتفاق:

```text
Agreement + Addon + Quantity + Unit Price + Status
```

### `store_rental_invoices`

فواتير دورية مستقلة:

```text
Base Amount + Addons Amount + Total
Period + Due Date + Payment Reference + Status
```

## الحزمة الأساسية المنفذة

1. عند اعتماد طلب متجر نهائيًا، ينشأ اتفاق إيجار تلقائي مرتبط بالعقد.
2. cron الإيجار يصدر فواتير دورية للاتفاقات المستحقة.
3. عند الاستحقاق غير المسدد، تتحول الفاتورة والاتفاق إلى `overdue`.
4. الأدمن يؤكد السداد برقم مرجع ويعيد الاتفاق إلى `active`.
5. الإضافات المدفوعة تضاف لاتفاق معين وتدخل الفاتورة الدورية التالية.

## حزمة فرض السعات (Entitlement Enforcement) — مكتملة

### محرك موحد وقابل للاختبار

أضيف الملف:

```text
lib/rentals/entitlements.ts
```

ويجمع بين:

- حدود باقة الاشتراك الأساسية:
  `maxProducts`, `maxEmployees`, `maxBranches`, `maxAnnouncements`, `maxNews`.
- الإضافات النشطة فقط، ضمن نافذة بدايتها/انتهائها.
- كمية الإضافة المخصصة للاتفاق.
- مزايا الباقة والإضافات كـ feature entitlements تمهيدًا للـ ERP وwhite-label والتقارير المتقدمة.

صيغة metadata القياسية لإضافة تزيد سعة عددية:

```json
{
  "limitKey": "maxBranches",
  "limitIncrease": 2,
  "features": ["branch_dashboard"]
}
```

أي أنها تضيف فرعين لكل كمية مفعّلة. ويمكن إزالة حد واحد فقط عبر:

```json
{
  "limitKey": "maxProducts",
  "unlimited": true
}
```

تم التحقق من هذه المفاتيح في API كتالوج الإضافات بدل قبول قيم سعة غير معروفة.

### الموارد التي تُفرض عليها الحدود الآن

| المورد | نقطة الفرض | قاعدة العد |
|---|---|---|
| المنتجات | إنشاء منتج التاجر | كل منتجات المتجر في الكتالوج |
| الموظفون | إنشاء موظف جديد | كل سجلات موظفي المتجر؛ تعديل موظف قائم لا يستهلك سعة جديدة |
| الفروع | طلب فرع/محل إضافي | فروع المجموعة غير المرفوضة، ويشمل المتجر الرئيسي |
| الإعلانات | إنشاء/تفعيل إعلان متجر | الإعلانات النشطة فقط |
| الأخبار | إنشاء/تفعيل خبر متحرك | الأخبار المتحركة النشطة فقط |

كما تم منع تجاوز الحد بتحويل مسودة إلى حالة `active` عبر مسارات تعديل الإعلان والخبر، وليس عبر الإنشاء فقط.

### اتساق التزامن

تُنفذ عملية العد والتحقق والإدراج داخل transaction واحد. أضيف PostgreSQL advisory lock بمفتاح المتجر قبل قراءة العداد، حتى لا تمر عمليتا إنشاء متزامنتان فوق نفس السعة.

### سياسة الانتقال للمتاجر القديمة

المتاجر التي لا تملك اتفاق إيجار بعد تعامل كـ `legacy` بدون حد مصطنع؛ لا تُحجب عملياتها بسبب الترحيل. عند ربط اتفاق نشط وباقة بها حدود يبدأ الفرض مباشرة. الاتفاقات `frozen` أو `terminated` أو `draft` تمنع توسيع الموارد؛ أما الإغلاق الآلي بعد المهلة فسيضاف في حزمة Grace/Freeze التالية.

## حزمة إثبات سداد الإيجار — مكتملة

### تدفق التاجر

1. تعرض صفحة `/merchant/billing` الفاتورة المفتوحة مع نموذج رفع إيصال صورة أو PDF.
2. يُرفع الملف عبر طبقة رفع الوسائط القائمة إلى مجلد `rental-payment-proofs/{invoiceId}`.
3. لا يقبل API رابطًا خارجيًا اعتباطيًا: يجب أن يطابق أصلًا مسجلًا في `media_assets` يملكه التاجر وأن يكون صورة أو PDF.
4. يرسل التاجر مرجع الحوالة وملاحظة اختيارية، ثم تتحول الفاتورة من `issued` أو `pending` أو `overdue` إلى `payment_submitted`.
5. يُخطر مسؤولو المنصة، ولا تتحول الفاتورة إلى `paid` ولا يعاد تفعيل الاتفاق لمجرد الرفع.

### تدفق الإدارة

- تظهر فواتير `payment_submitted` ضمن `/admin/rentals` مع رابط فتح الإثبات والمرجع والملاحظة.
- **اعتماد الإثبات:** يحول الفاتورة إلى `paid`، يسجل وقت السداد، يعيد الاتفاق إلى `active`، ويخطر التاجر.
- **رفض الإثبات:** يتطلب سببًا ظاهرًا للتاجر، ويحفظ قرار الرفض، ثم يعيد الفاتورة إلى `issued` أو `overdue` بحسب تاريخ الاستحقاق كي يستطيع التاجر رفع بديل.
- يظل مسار `تأكيد سداد يدوي` متاحًا للأدمن للحالات خارج الرفع الإلكتروني.

### الحفظ والتدقيق

- تحفظ بيانات الإثبات في `store_rental_invoices.metadata` مع معرف `media_asset`، المرجع، المرسل، وحالة المراجعة.
- عند إعادة الرفع بعد رفض، يحتفظ النظام بالإثبات السابق في `paymentProofHistory` (حتى 20 عنصرًا) بدل حذفه.
- سجل audit يغطي الرفع والاعتماد والرفض، وتصل إشعارات للتاجر/الأدمن في كل نقطة رئيسية.
- لا يوجد migration جديد: حقل `metadata` الموجود في الفاتورة استُخدم عمدًا للحفاظ على سجل الإثباتات المرن.

> ملاحظة تشغيلية: خصوصية رابط الإيصال تعتمد على مزود الوسائط الفعلي. قبل الإنتاج يجب ضبط `MEDIA_PROVIDER` على Cloudinary أو S3/R2 وفق سياسة الوسائط وعدم الاعتماد على التخزين المحلي/inline.
