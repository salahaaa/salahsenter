# تقرير تنفيذ: Dynamic Homepage Exposure & Revenue Engine

**التاريخ:** 2026-07-15  
**الحالة:** مكتمل محلياً — نتائج التحقق النهائي تضاف في نهاية التقرير.

## القرار التنظيمي
لم تُحمَّل نافذة **«قواعد ظهور الواجهة الرئيسية»** مسؤوليات الإعلان والفوترة. بقيت مخصصة للترتيب العضوي، وأنشئ مركز مستقل:

```text
/admin/home-exposure-revenue
```

ويظهر من لوحة الإدارة باسم **«محرك ظهور وإيرادات الرئيسية»**.

## ما تم تنفيذه

### 1) كتالوج مساحات تجارية للرئيسية
تمت إضافة مواضع ديناميكية للبنر الرئيسي وPromo، المتاجر المميزة/الرائجة/الأحدث، المنتجات المميزة/الرائجة/الأحدث، العروض المميزة واليومية ونهاية الأسبوع والموسمية، الأجنحة، مساحة إعلانات المول، والمنتجات الممولة.

كل ظهور من المحرك:
- يظهر في مساحة مستقلة عن المحتوى العضوي؛
- يحمل وسم **«إعلان ممول»**؛
- يحفظ موضعه في أحداث القياس؛
- لا يغيّر ترتيب المتاجر أو المنتجات العضوي خفية.

### 2) الجدولة والتدوير
- دائم، فترة تاريخية، نافذة يومية، أيام أسبوعية مع ساعات، أول أسبوع من كل شهر، وخانات مخصصة.
- المنطقة الزمنية الافتراضية: `Asia/Aden`.
- يدعم المثالين المطلوبين: الجمعة 18:00–00:00، وأول أسبوع من كل شهر.
- سياسات مستقلة لكل موضع: عدد البطاقات، الحد الأقصى من المتجر نفسه، دورة التدوير بالدقائق، ونمط ترتيب افتراضي.
- التدوير العادل موزون وحتمي داخل bucket زمني؛ لذلك لا يبتلع متجر واحد المساحة ولا يحصل المستخدم على ترتيب عشوائي غير قابل للتفسير.

### 3) الترتيب والعدالة
لكل حملة: أولوية يدوية، أولوية مدفوعة، وزن تدوير، ونمط ترتيب: يدوي، مزايدة، نقرات نظيفة، تحويل، أو تدوير عادل.

يحمي المحرك الواجهة عبر:
- حد عناصر لكل متجر في الموضع؛
- حد عدد بطاقات لكل موضع؛
- استبعاد الحملة المنتهية أو خارج جدولها أو التي بلغ حدها؛
- فحص إضافي في API التتبع، وليس في الواجهة فقط.

### 4) العدادات والحدود والإيقاف
الترحيل الجديد `0071_dynamic_homepage_exposure_revenue_engine` يضيف:

```text
ad_campaign_delivery_counters
```

ويحافظ PostgreSQL على عدادات الظهور والنقرات والنقرات النظيفة والتحويلات والإيراد المنسوب وإيراد المنصة بواسطة triggers متزامنة مع الأحداث.

- حد الظهور يعتمد impressions.
- حد النقرات يعتمد **النقرات النظيفة** بعد فحص الاحتيال.
- بعد آخر حدث مسموح، توقف الحملة تلقائياً، يسجل سبب الإيقاف، يرسل إشعاراً للتاجر، ويبطل cache للرئيسية.
- صفحة قديمة مفتوحة لا تستطيع تجاوز الحد؛ فـ API يعيد فحص الجدول والعداد تحت قفل حملة قبل تسجيل الحدث.

### 5) الإيرادات
- **CPC وCPM** يستفيدان من مسار الإعلانات الموجود: مقاومة الاحتيال، الحجز التشغيلي، دفتر `ad_billing`، وفواتير الإعلانات. لا يوجد تحصيل من أموال العملاء.
- خيارات المدة والزيارة والتحويل متاحة كتوصيف وتشغيل إداري مستقبلي فقط؛ لا تنشئ خصماً أو فاتورة تلقائية إلى أن تعتمد سياسة تسعير وإثبات ومصالحة مستقلة.
- «إيراد الإعلان» في اللوحة هو إيراد إعلان مسجل/مستحق في الدفتر، وليس إقراراً بتحصيل فعلي.

### 6) لوحة الإدارة
توفر الصفحة الجديدة:
- إضافة ظهور تجاري مرتبط بمتجر ومساحة رئيسية.
- اختيار نموذج تجاري، حالة أولية، ميزانيات ومزايدة عند CPC/CPM.
- تعديل الجدولة، الأولوية، حدود الظهور والنقرات، الرابط، المحتوى الإعلاني، وتمديد النهاية.
- إيقاف فوري أو إعادة تفعيل.
- عدادات الظهور والنقرات النظيفة والتحويلات وإيراد الإعلان والوقت المتبقي والحد المتبقي.
- إعدادات العدالة والتدوير لكل موضع.
- إمكانية ربط الظهور بمتجر أو منتج أو عرض أو جناح أو بنر بواسطة نوع ومعرف المحتوى المستهدف؛ يستخدم المحرك رابطاً مناسباً عند توفر الهدف.

## الأداء والصيانة
- مرشحو المحرك محدودون بـ300 حملة في قراءة الواجهة، والمختارون محدودون بسياسة الموضع.
- عداد مستقل وindex مركب على موضع/حالة/نافذة الحملة يمنعان المسح المتكرر للأحداث عند الوصول إلى نطاق كبير.
- تم تعطيل Full Route Cache للرئيسية، مع إبقاء بيانات الصفحة في cache بمفتاح bucket دقيقة؛ فلا يستمر إعلان منتهي أو نافذة زمنية منتهية 120 ثانية بسبب ISR.
- أي تعديل إداري أو توقف تلقائي يبطل cache فوراً.
- لا توجد queue جديدة أو secrets أو مزود خارجي أو تعديل لأموال العملاء.

## الترحيل والتراجع
- الترحيل إضافي فقط ولا يحذف بيانات أو فواتير قائمة.
- Rollback التشغيلي: إيقاف `enabled` من إعدادات المحرك أو إزالة استهلاك المواضع من الصفحة؛ تبقى البيانات التاريخية والفواتير سليمة.
- Rollback لقاعدة البيانات بعد إيقاف التطبيق الجديد: إزالة triggers والدوال والـ index ثم جدول العدادات، كما هو موثق في رأس migration.

## حدود معروفة قبل Production
1. لم يطبق الترحيل على قاعدة Staging أو Production في هذه البيئة.
2. لم تنفذ تجربة PostgreSQL حية لتأكيد triggers أو مسار الأحداث كاملاً.
3. لا يوجد Load Test/Redis/Staging browser session ضمن هذه الدفعة؛ يلزم ذلك قبل الإطلاق، خصوصاً لحملات عالية المرور.
4. نماذج مدة/زيارة/تحويل لا تفوتر تلقائياً عمداً.
5. لم يُشغّل `next build` بسبب قيد ذاكرة Arena المعروف؛ يجب تأكيده في GitHub Actions/Vercel بعد تطبيق migration على Staging.
