# تصميم التغيير: الجناح هو قطاع النشاط الوحيد في طلب فتح المتجر

**التاريخ:** 2026-07-16  
**الحالة:** منفذ محلياً — غير مطبق على Staging أو Production

## القرار المعتمد

لا يختار التاجر جناحاً وقطاعاً بصورة منفصلة.

- **الجناح = قطاع النشاط** في رحلة طلب فتح المتجر.
- يختار التاجر الجناح مرة واحدة فقط، مثل: «الأزياء».
- يربط الأدمن كل جناح بقالب تجهيز واحد مناسب، مثل: `fashion`.
- يستخرج الخادم مفتاح القالب من الجناح المختار، ولا يقبل مفتاحاً مرسلاً من المتصفح.
- بعد اعتماد المتجر، ينقل الاختيار إلى المتجر ويظهر له قالب قطاعه فقط في أدوات التجهيز.

هذا يمنع ازدواج المعنى والاختيار، ويجعل العلاقة قابلة للإدارة من لوحة الأدمن دون تعديل برمجي لكل جناح جديد.

## تصميم البيانات

Migration `0081_wing_is_single_activity_sector` تضيف:

```text
wings.activity_template_key
```

- المفتاح منطقي وليس FK ثابتاً، لأنه قد يشير إلى قالب نظامي أو إلى قطاع يضيفه الأدمن في الكتالوج.
- يبقى nullable لحماية الأجنحة الحالية؛ الجناح غير المربوط لا يظهر في نموذج طلب المتجر حتى يربطه الأدمن.
- تم عمل backfill محدود وآمن لأسماء أجنحة seed الأصلية فقط، بلا تخمين أو إعادة تصنيف لأجنحة العملاء.

## الواجهة والـ API

### التاجر

- يظهر حقل واحد: **«الجناح / قطاع النشاط»**.
- الرسالة توضح أن الجناح يحدد قالب التجهيز تلقائياً ولا يوجد اختيار قطاع ثانٍ.
- تنطبق القاعدة ذاتها على طلب متجر مستقل وإعادة إرسال طلب تعديل.

### الأدمن

في **إدارة الأجنحة**:

- عند إنشاء أو تعديل جناح، يختار الأدمن «قالب تجهيز الجناح (قطاع التاجر)».
- لا يقبل API إنشاء جناح جديد بلا قالب.
- لا يسمح API بفصل القالب عن جناح قائم؛ يمكن تعطيل الجناح إن لم يكن جاهزاً.
- يتحقق API أن القالب المختار نشط فعلاً.

### الخادم

- لا يرسل نموذج التاجر `activityTemplateKey`.
- `resolveActivityTemplateForWing(wingId)` يتحقق من الجناح النشط وقالب التجهيز النشط، ثم يحفظ المفتاح المستخرج في طلب التاجر.
- لا تظهر في نموذج التاجر إلا الأجنحة النشطة ذات الرابط الصحيح.

## حساب التوسع والصيانة

| المجال | القرار |
|---|---|
| البيانات | عمود نصي قصير مفهرس على `wings`؛ لا إنشاء جدول ربط أو قراءة لكل منتج. |
| القراءة | تحميل الأجنحة الصالحة يقرأ الأجنحة النشطة وقائمة القوالب النشطة مرة واحدة ويستبعد أي ربط غير صالح. |
| الكتابة | ربط جناح بالقالب عملية أدمن مدققة؛ استخراج المفتاح عند تقديم الطلب قراءة واحدة. |
| التوافق | لا تغيير صامت للأجنحة أو المتاجر القديمة. |
| الصيانة | لوحة الأجنحة هي نقطة الصيانة الوحيدة لخريطة الجناح ← القالب. |
| المراقبة | الأخطاء تمنع الطلب برسالة محددة عندما يكون الجناح أو القالب معطلاً؛ لا توجد Queue أو تخزين خارجي جديد. |

## الأمن والحوكمة

- الخادم هو مصدر الحقيقة للعلاقة بين الجناح والقالب.
- لا يستطيع التاجر اختيار قالب لا يطابق الجناح، حتى عبر استدعاء API مباشر.
- لا تمس هذه العملية السعر أو المخزون أو النشر أو الأموال أو العقد.
- التغييرات الإدارية على الجناح مسجلة في audit log الموجود.

## Rollback

موثق داخل migration: إزالة الفهرس ثم العمود بعد نشر كود لا يقرأه. لا ينفذ rollback تلقائياً على بيئة حية.

## تحقق لاحق مطلوب في Staging

1. ربط جناح «الأزياء» بقالب `fashion` من إدارة الأجنحة.
2. تقديم طلب متجر واختيار «الأزياء» فقط.
3. محاولة إرسال مفتاح قالب مختلف ضمن HTTP يدوي والتأكد من أن الخادم يستخرج مفتاح الجناح لا يقبل الإدخال.
4. اعتماد الطلب والتأكد أن أدوات التاجر لا تعرض إلا قالب الأزياء.
