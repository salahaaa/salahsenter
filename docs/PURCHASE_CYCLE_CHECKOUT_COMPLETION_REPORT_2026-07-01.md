# تقرير استكمال دورة الشراء من التاجر حتى إغلاق الطلب

التاريخ: 2026-07-01

## الهدف

إعادة فحص دورة الشراء كاملة ابتداءً من تهيئة التاجر لطرق الدفع والشحن، مروراً بسلة العميل والدفع، وانتهاءً بإغلاق الطلب، مع مراعاة فصل الشراء عند وجود منتجات من متجرين أو أكثر.

---

## المشاكل التي تم رصدها

1. السلة كانت تعمل غالباً داخل صفحة المتجر فقط، ولا توجد صفحة Checkout مركزية واضحة.
2. العميل لم يكن يختار وسيلة الدفع والشحن قبل إنشاء الطلب.
3. عند وجود منتجات من أكثر من متجر، لم تكن هناك تجربة Checkout واضحة تفصل الطلبات حسب المتجر.
4. API الطلب كان يدعم `paymentMethodId` و `shippingMethodId`، لكن لم يكن يفرض اختيارهما بشكل واضح.
5. إغلاق الطلب لم يكن يضمن تأكيد الدفع قبل الإغلاق.
6. الشراء السريع كان ينشئ طلباً مباشرة بدون المرور بخطوة اختيار الدفع والشحن.

---

## ما تم تنفيذه

### 1. صفحة Checkout مركزية

تمت إضافة صفحة:

```txt
/checkout
```

الملفات:

```txt
app/checkout/page.tsx
components/checkout/multi-store-checkout.tsx
```

وظائف الصفحة:

- قراءة السلة المحلية `salah_center_cart`.
- تجميع المنتجات حسب المتجر.
- عرض كل متجر في قسم مستقل.
- اختيار وسيلة دفع مستقلة لكل متجر.
- اختيار وسيلة شحن مستقلة لكل متجر.
- إدخال بيانات التوصيل مرة واحدة.
- إضافة ملاحظة لكل متجر.
- إنشاء طلب مستقل لكل متجر.

---

### 2. فصل الشراء من متجرين أو أكثر

تم تنفيذ منطق واضح:

```txt
سلة متعددة المتاجر → Checkout → تقسيم حسب storeId → طلب مستقل لكل متجر
```

مثال:

```txt
منتجات من متجر A + منتجات من متجر B
```

ينتج عنها:

```txt
Order A لمتجر A
Order B لمتجر B
```

وهذا يضمن:

- محاسبة مستقلة لكل متجر.
- شحن مستقل لكل متجر.
- حالة طلب مستقلة لكل متجر.
- إشعارات مستقلة لكل تاجر.
- عدم خلط منتجات متجرين في طلب واحد.

---

### 3. API خيارات الدفع والشحن للـ Checkout

تمت إضافة:

```txt
app/api/checkout/options/route.ts
```

وظيفته:

- استقبال `storeIds`.
- إرجاع طرق الدفع الفعالة لكل متجر.
- إرجاع طرق الشحن الفعالة لكل متجر.
- إرجاع إعدادات الطلب لكل متجر مثل أقل مبلغ طلب وسياسات الشحن.

---

### 4. تعديل الشراء السريع

تم تعديل:

```txt
components/product/product-detail.tsx
components/store/storefront-experience.tsx
components/offers/offer-checkout-panel.tsx
```

بدلاً من إنشاء الطلب مباشرة، يتم الآن:

1. إضافة المنتج أو العرض إلى السلة.
2. تحويل العميل إلى:

```txt
/checkout
```

حتى يختار:

- وسيلة الدفع.
- وسيلة الشحن.
- بيانات التوصيل.

---

### 5. تقوية API إنشاء الطلب

تم تعديل:

```txt
app/api/orders/route.ts
```

الإضافات:

- فرض اختيار وسيلة الدفع إذا كانت هناك وسائل دفع مفعلة.
- رفض الطلب إذا لم يهيئ المتجر أي وسيلة دفع مفعلة.
- فرض اختيار وسيلة الشحن إذا كانت هناك وسائل شحن مفعلة.
- رفض الطلب إذا لم يهيئ المتجر أي وسيلة شحن مفعلة.
- التحقق من أقل مبلغ طلب من إعدادات المتجر.
- دعم `autoAcceptOrders` من إعدادات المتجر:
  - إذا مفعّل، يبدأ الطلب بالحالة `confirmed`.
  - إذا غير مفعّل، يبدأ بالحالة `new`.

مع بقاء:

- Atomic inventory reservation.
- Idempotency-Key.
- فصل الطلب حسب متجر واحد فقط.

---

### 6. دورة إغلاق الطلب والدفع

تم تعديل:

```txt
app/api/orders/[id]/status/route.ts
components/merchant/order-status-actions.tsx
```

الإضافات:

- التاجر يستطيع تحديث حالة الدفع:
  - pending
  - paid
  - failed
  - refunded
- لا يمكن إغلاق الطلب `closed` قبل تأكيد الدفع `paid`.
- عند تحديث حالة الدفع، يتم تحديث `orders.paymentStatus` و `order_payments`.
- أزرار التاجر أصبحت تشمل:
  - تأكيد الدفع.
  - استرداد.
  - فشل الدفع.
  - حالات الطلب التشغيلية حتى الإغلاق.

## دورة الشراء الجديدة

### من جهة التاجر

1. يهيئ وسائل الدفع من:

```txt
/merchant/operations-settings
```

2. يهيئ وسائل الشحن من نفس الصفحة.
3. يضبط إعدادات الطلب:
   - قبول تلقائي.
   - أقل مبلغ طلب.
   - سياسة الشحن.
   - سياسة الإرجاع.

### من جهة العميل

1. يضيف منتجات من متجر أو أكثر إلى السلة.
2. يدخل إلى:

```txt
/checkout
```

3. يرى السلة مقسمة حسب المتجر.
4. يختار لكل متجر:
   - وسيلة دفع.
   - وسيلة شحن.
5. يؤكد الشراء.
6. يتم إنشاء طلب مستقل لكل متجر.

### من جهة النظام

لكل متجر:

1. إنشاء طلب مستقل.
2. إصدار فاتورة.
3. حجز المخزون Atomic.
4. إنشاء سجل دفع وشحن.
5. إرسال jobs للإشعارات والولاء.

### من جهة التاجر بعد الطلب

1. مراجعة الفاتورة.
2. تأكيد الطلب.
3. تأكيد الدفع.
4. تجهيز الطلب.
5. جاهز للشحن.
6. تم الشحن.
7. تم التسليم.
8. إغلاق الطلب بعد الدفع.

## ملاحظات مهمة

1. لم يتم تشغيل `db:seed`.
2. لم تتم إضافة migrations جديدة لهذه المرحلة.
3. ما زالت طرق الدفع الحالية `manual`، أي أن الدفع الإلكتروني الفعلي يحتاج تكامل بوابة دفع لاحقاً.
4. تم تجهيز الدورة لتدعم بوابات الدفع لاحقاً عبر `paymentMethods.provider/config` و `order_payments`.
5. عند فشل إنشاء طلب لمتجر ضمن checkout متعدد المتاجر بعد إنشاء طلبات سابقة، تعرض الواجهة تنبيهاً للعميل بعدد الطلبات التي أنشئت، لأن الفصل بين المتاجر يعني أن كل طلب مستقل.

---

## توصيات المرحلة التالية

1. إضافة بوابة دفع فعلية وربطها بـ `order_payments`.
2. إضافة صفحة دفع نهائية/تأكيد دفع حسب provider.
3. إضافة تحديث رقم التتبع والشحن.
4. إضافة قيود أكثر تفصيلاً على انتقال حالات الطلب.
5. إضافة اختبارات تزامن checkout متعددة المتاجر.
