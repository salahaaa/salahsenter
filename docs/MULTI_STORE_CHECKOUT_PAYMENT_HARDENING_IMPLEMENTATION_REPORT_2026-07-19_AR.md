# تقرير تطوير وتقوية دورة Checkout والدفع متعددة المتاجر

**التاريخ:** 2026-07-19  
**النطاق:** معالجة نقاط الضعف التي ظهرت في تدقيق شراء المتسوق من متجرين مختلفين، مع الحفاظ على النموذج المعتمد `merchant_collects` وعدم تحويل المنصة إلى وسيط مالي.

## القرارات التي حُفظت

```text
سلة واحدة للعميل
→ طلب مستقل لكل متجر
→ شحن مستقل لكل متجر
→ دفع مستقل لكل متجر
→ العميل يدفع للتاجر مباشرة
```

لا يوجد طلب موحد أو فاتورة موحدة أو تسوية أموال عميل موحدة لمتجرين، لأن ذلك يتعارض مع استقلال المتاجر والشحن الذي يديره التاجر ونموذج الأموال الحالي.

## الإصلاحات المنفذة

### 1. منع تكرار طلب متجر نجح عند فشل متجر آخر

#### قبل الإصلاح

كان Checkout ينفذ المتاجر بالتتابع. إذا نجح A وفشل B، يمكن أن تبقى منتجات A في السلة؛ إعادة المحاولة قد تنشئ طلباً جديداً لـA.

#### بعد الإصلاح

- مفتاح idempotency أصبح ثابتاً لكل متجر/محتوى محاولة داخل `localStorage` بدلاً من قيمة عشوائية في كل إعادة محاولة.
- بعد نجاح طلب متجر، تزال بنوده فوراً من السلة المحلية.
- خادم إنشاء الطلب يزيل بنود ذلك المتجر من السلة الخادمية **ضمن transaction إنشاء الطلب نفسها**.
- في النجاح الجزئي يبقى المتجر الفاشل فقط في السلة لإعادة المحاولة.

النتيجة:

```text
A نجح + B فشل
→ A لا يعود للسلة
→ إعادة المحاولة تنفذ B فقط
```

### 2. مسار دفع واضح لكل طلب

- صفحة نتيجة Checkout تعرض الآن زر:

```text
إتمام الدفع
```

لكل طلب غير مدفوع، ويرتبط بالمسار:

```text
/checkout/payment/[orderId]
```

- صفحة تفاصيل الطلب تعرض الزر نفسه للعميل.
- توضح صفحة النتيجة أن المنصة لا تجمع المدفوعات في عملية واحدة عبر المتاجر.
- صفحة الدفع اليدوي تعرض تعليمات وسيلة التاجر الآمنة، وتعرض نموذج إثبات الدفع فقط عندما تطلبه الوسيلة.
- COD لا يطلب إثبات تحويل؛ يعرض تعليمات الدفع عند الاستلام فقط.

### 3. معالجة العملات المتعددة

- API خيارات Checkout يعيد العملة الافتراضية ومعدل التحويل الخاص بكل متجر.
- أسعار المنتجات والشحن والكوبون والطلب الفرعي تظهر بعملة المتجر.
- استُبدل «الإجمالي الموحد» الذي كان يجمع أرقام عملات مختلفة بملخص:

```text
إجمالي كل متجر حسب عملته
```

وبذلك لا تعرض الواجهة جمعاً مضللاً بين YER وSAR أو USD.

### 4. المخزون في COD والتحويل اليدوي

#### قبل الإصلاح

في `STANDALONE` كان مخزون الطلب يخصم مباشرة عند إنشاء الطلب رغم أن الدفع قد يبقى `pending`.

#### بعد الإصلاح

- عند إنشاء الطلب: يحجز المخزون فقط.
- يخصم المخزون الحقيقي في Standalone عند تحقق الشرطين معاً:

```text
paymentStatus = paid
و
statusCode = delivered أو closed
```

- أضيفت خدمة موحدة:

```text
lib/commerce/order-inventory-completion.ts
```

وتستدعى من:

- تحديث حالة الطلب من التاجر/الأدمن.
- webhook البوابة المحلية.
- webhook Stripe.
- اعتماد إثبات الدفع اليدوي.

الخدمة idempotent عبر `reservationStatus`; لا تخصم مرة ثانية بعد تحرير الحجز.

- عند الإلغاء، يعاد فقط ما خُصم فعلياً؛ أما المخزون المحجوز فقط فيفك حجزه بلا زيادة مخزون خاطئة.

### 5. حماية نموذج merchant_collects في ERP

كانت بعض معالجات أحداث ERP تستدعي settlement داخلياً عند الدفع والتسليم/الإغلاق.

تمت إضافة الحماية:

```text
platformIsFinancialIntermediary()
```

فلا ينشأ settlement أو رصيد/سحب داخلي في وضع:

```text
PLATFORM_CUSTOMER_MONEY_MODE=merchant_collects
```

ويبقى التحصيل للمتجر مباشرة.

## ما بقي مطلوباً قبل إطلاق تشغيلي حقيقي

لا يوجد اختبار قاعدة بيانات/بوابة حقيقية في Arena. يجب تنفيذ سيناريو Staging التالي:

```text
1. متجر A + متجر B، COD/COD.
2. متجر A + متجر B، تحويل يدوي/تحويل يدوي.
3. نجاح A وفشل B ثم إعادة المحاولة: يجب أن يبقى B فقط في السلة.
4. Stripe أو بوابة محلية لطلبين: جلسة مستقلة لكل طلب.
5. دفع بعد وصول الطلب إلى delivered: يجب إنهاء المخزون مرة واحدة فقط.
6. إلغاء قبل الدفع: يجب فك الحجز فقط.
7. إلغاء بعد الدفع/التسليم: يجب استعادة المخزون وفق دورة الإرجاع.
8. متجران بعملتين مختلفتين: لا يظهر إجمالي موحد مضلل.
9. حدث ERP paid/delivered في merchant_collects: لا ينشئ ledger أو payout للمتجر.
```
