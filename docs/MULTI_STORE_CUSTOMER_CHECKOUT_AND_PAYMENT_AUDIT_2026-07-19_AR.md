# تدقيق دورة شراء العميل من متجرين مختلفين والدفع

**التاريخ:** 2026-07-19  
**نوع التدقيق:** مراجعة مصدر محلية فقط. لم يتم إنشاء طلبات أو تشغيل دفع أو webhook أو قاعدة بيانات Staging/Production.

## النتيجة التنفيذية

النظام الحالي لا ينشئ «طلباً موحداً» يضم متجرين. عند وجود متجرين في السلة فإنه ينشئ:

```text
طلب A مستقل للمتجر A
طلب B مستقل للمتجر B
```

وهذا صحيح ومتوافق مع القرار التشغيلي المعتمد:

```text
الشحن يديره التاجر
الدفع الأول نقداً
PLATFORM_CUSTOMER_MONEY_MODE=merchant_collects
```

أي أن المنصة لا تجمع أموال العميل ثم توزعها؛ العميل يدفع لكل تاجر وفق وسيلة المتجر وطلبه المستقل.

## رحلة العميل الفعلية

### 1. السلة

- السلة تسمح بمنتجات من عدة متاجر.
- كل بند يحمل `storeId` محفوظاً من الخادم، ولا يثق النظام بسعر العميل.
- السلة ترفض المنتج غير النشط أو المنتج `SHOWCASE_ONLY` أو المنتج خارج فترة النشر.

### 2. صفحة Checkout

`MultiStoreCheckout` يقسم السلة في الواجهة حسب `storeId`.

لكل متجر يظهر للعميل بشكل مستقل:

- منتجات ذلك المتجر فقط.
- طريقة دفع ذلك المتجر.
- طريقة شحن ذلك المتجر والتغطية الجغرافية والرسوم.
- كوبون خاص بذلك المتجر.
- ملاحظة خاصة بذلك المتجر.
- إجمالي فرعي ورسوم شحن خاصة به.

العنوان واحد للعميل، لكن التغطية تتحقق لكل متجر على حدة وفق المحافظة/المدينة/المنطقة.

### 3. إنشاء الطلبات

الواجهة ترسل طلباً منفصلاً إلى:

```text
POST /api/orders
```

لكل متجر **بالتتابع**، ومعه `Idempotency-Key` خاص بذلك المتجر.

الخادم لكل طلب منفصل يتحقق من:

- أن كل المنتجات تتبع المتجر المختار نفسه.
- السعر والمخزون والنشاط وفترة النشر من الخادم.
- الحد الأدنى للطلب الخاص بالمتجر.
- وسيلة دفع صالحة لذلك المتجر.
- وسيلة شحن وتغطية صالحتين للعنوان.
- الكوبون من جديد على الخادم.

ثم ينشئ لكل متجر:

```text
orders
order_items
order_payments
order_shipments
order_status_history
```

وفاتورة مستقلة حسب وضع ERP/Standalone.

### 4. بعد الإنشاء

- العميل يرى رقمين مستقلين للطلبين.
- كل تاجر يتلقى إشعاراً لطلب متجره فقط.
- الشحن والتتبع والحالة والإلغاء والنزاع والإرجاع مرتبطة بكل طلب وحده.
- لا يوجد رقم شحنة موحد ولا فاتورة واحدة لمتجرين، وهذا هو السلوك الصحيح في نموذج الشحن الذي يديره التاجر.

## الدفع عند الشراء من متجرين

### أ. الدفع النقدي عند الاستلام — النموذج الحالي الموصى به

إذا اختار العميل COD لكلا المتجرين:

```text
طلب A: يدفع العميل قيمة A + شحن A عند تسليم متجر A.
طلب B: يدفع العميل قيمة B + شحن B عند تسليم متجر B.
```

- مبلغ كل طلب مستقل.
- قد يصل الشحن في يومين مختلفين ومن مندوبين مختلفين.
- لا يوجد تحصيل أو تسوية أو رصيد تاجر داخل المنصة في وضع `merchant_collects`.
- حالة الدفع تبدأ `pending` ويؤكدها التاجر عند التحصيل/التسليم وفق صلاحياته.

### ب. تحويل/محفظة/حوالة يدوية

لكل متجر تعليماته وحسابه/محفظته الخاصة.

- العميل يرفع إثبات دفع **لكل طلب**.
- تاجر الطلب نفسه يراجع الإثبات ويقبله أو يرفضه.
- قبول الإثبات يحدث حالة الدفع لذلك الطلب فقط.

### ج. بوابة دفع إلكترونية أو Stripe

المسار مصمم لكل `orderId` منفرد:

```text
POST /api/payments/checkout
```

لذلك شراء متجرين يحتاج جلسة دفع مستقلة لكل طلب، ولا توجد جلسة بوابة موحدة تجمع متجرين. هذا متوافق مع عدم كون المنصة وسيطاً مالياً.

## نقاط القوة

- فصل قوي للمتاجر على مستوى `orders.storeId`.
- السعر والخصم والشحن يعاد حسابها من الخادم لكل متجر.
- الكوبون لا يعبر المتاجر بلا تحقق.
- حماية replay/webhook موجودة لبوابات الدفع.
- `Idempotency-Key` لكل إنشاء طلب.
- التتبع والمرتجعات والنزاعات والفواتير معزولة لكل متجر.
- لا يوجد payout افتراضي لأموال العميل في وضع `merchant_collects`.

## ملاحظات ومخاطر مكتشفة

### P1 — فشل جزئي قد يترك منتجات متجر نجح في السلة

الواجهة تنشئ طلبات المتاجر بالتتابع. إذا نجح طلب المتجر A ثم فشل B:

- تنتقل الواجهة إلى نتيجة توضح النجاح الجزئي.
- لكن تنظيف السلة يحدث فقط بعد نجاح **كل** المجموعات.
- لذلك يمكن أن تبقى منتجات A الناجحة في السلة محلياً.
- إعادة المحاولة قد تنشئ طلباً جديداً لـA لأن مفتاح idempotency الجديد عشوائي في المحاولة الجديدة.

**المطلوب:** سجل Checkout Group/Session دائم يربط المتاجر، أو تنظيف بنود المتاجر الناجحة فوراً مع حالة إعادة محاولة للمتاجر الفاشلة فقط.

### P1 — رحلة الدفع الإلكتروني متعددة المتاجر غير مكتملة في النتيجة

بعد إنشاء الطلبين، صفحة النتيجة تعرض تفاصيل وتتبع لكل طلب، لكنها لا تعرض مساراً واضحاً مثل:

```text
ادفع طلب المتجر A
ادفع طلب المتجر B
```

مع أن صفحة الدفع الفردي موجودة:

```text
/checkout/payment/[orderId]
```

والبوابة فعلياً تتعامل مع طلب واحد فقط.

**المطلوب:** صفحة دفع دفعي تعرض قائمة الطلبات غير المدفوعة وتبدأ الدفع بالترتيب، أو روابط دفع مستقلة وواضحة لكل طلب في صفحة النتيجة وتفاصيل الطلب.

### P1 — ملخص العملات المتعددة غير آمن كمبلغ موحد

كل طلب يستخدم العملة الافتراضية لمتجره، بينما ملخص Checkout يجمع أرقام المتاجر مباشرة دون إظهار عملة لكل صف أو منع جمع عملات مختلفة.

**المطلوب:**

- إظهار عملة كل متجر صراحة.
- منع إظهار «إجمالي موحد» عند اختلاف العملات، أو تحويله بسعر صرف موثق ومعلن قبل التأكيد.

### P1 — خصم المخزون في وضع Standalone يحدث قبل تأكيد الدفع

في وضع `STANDALONE`، بعد إنشاء الطلب وحجز المخزون، ينفذ النظام إنهاء الحجز وخصم المخزون/إنشاء الفاتورة حتى لو بقي الدفع `pending`.

هذا قد يكون قراراً مقبولاً إذا كان إنشاء الطلب يمثل بيعاً ملزماً، لكنه يحتاج سياسة صريحة لـ:

```text
COD غير مؤكد
تحويل يدوي غير مقبول بعد
انتهاء مهلة الدفع
إلغاء تلقائي واستعادة المخزون
```

حالياً انتهاء الحجز اختياري بحسب إعدادات التاجر، ولذلك يجب اختبار هذا المسار في Staging قبل الإطلاق.

### P1 — مسار ERP قد ينشئ settlement داخلياً خلاف سياسة merchant_collects

المسار العادي يستخدم `MerchantCollectsRevenueService` ولا ينشئ رصيداً/سحباً للتاجر. لكن بعض معالجات أحداث ERP تستدعي `settleClosedPaidOrder` مباشرة عند حالة مدفوع ومسلّم/مغلق.

**المطلوب:** إضافة حماية `platformIsFinancialIntermediary()` داخل مسارات settlement الخاصة بـERP، حتى لا تنشأ أرصدة أو قيود تسوية في وضع الإطلاق `merchant_collects`.

## مثال عملي متوقع

السلة:

```text
متجر A: منتجات = 20,000 + شحن 2,000
متجر B: منتجات = 15,000 + شحن 1,500
```

مع COD:

```text
ORD-A = 22,000 للتاجر A عند تسليم شحنته.
ORD-B = 16,500 للتاجر B عند تسليم شحنته.
```

لا يوجد مبلغ 38,500 يدخل حساب المنصة كوسيط مالي.

## التوصية قبل الإطلاق التشغيلي

لا تطلق الدفع الإلكتروني متعدد المتاجر أو العملات المتعددة قبل إصلاح نقاط P1 واختبار السيناريو التالي على Staging:

```text
A + B في السلة
→ COD/COD
→ تحويل/تحويل
→ COD/تحويل
→ بوابة/بوابة
→ نجاح A وفشل B
→ إعادة محاولة B فقط
→ إلغاء A
→ إثبات دفع B وقبوله/رفضه
→ تسليم متاجر في أوقات مختلفة
→ إرجاع طلب واحد فقط
```

## الخلاصة

دورة COD متعددة المتاجر منطقية حالياً من ناحية الفصل التجاري:

```text
سلة واحدة للعميل
→ طلب مستقل لكل متجر
→ شحن مستقل لكل متجر
→ دفع مباشر مستقل لكل تاجر
→ متابعة/إرجاع مستقل لكل طلب
```

لكنها ليست جاهزة بعد كدورة دفع إلكتروني متعددة المتاجر بمستوى إطلاق تشغيلي كامل حتى تعالج نقاط P1 أعلاه.
