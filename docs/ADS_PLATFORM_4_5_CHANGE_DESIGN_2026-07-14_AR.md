# 4.5 — تصميم استكمال منصة الإعلانات قبل التنفيذ

**التاريخ:** 14 يوليو 2026  
**الحالة:** تصميم تنفيذ معتمد وفق قاعدة: **لا إضافة بدون حساب التوسع، ولا إضافة بدون حساب الصيانة.**

## الهدف والنطاق

تحويل الإعلانات من إدارة حملات وبنرات فقط إلى دورة واضحة وقابلة للتدقيق تشمل:

1. ظهور Sponsored Products/Banners بقياس موثوق، مواضع عرض معلنة، وعدم عرض مخزون نافد أو متجر غير نشط.
2. تسعير CPC أو CPM، سقف/وتيرة ميزانية، حجز تشغيلي للميزانية، دفتر تكاليف، وفواتير دورية للتاجر.
3. CTR / CVR / ROAS / الإيراد المنسوب، إشارات منع النقرات المشبوهة، وإطار A/B creative وتوصية bid/budget قابلة للتفسير.
4. فصل نتائج `sponsored` عن `organic` في واجهة المستخدم ومنطق الترتيب.

### خارج النطاق في هذه الحزمة

- لا يتم خصم أموال أو حفظ بطاقات أو اعتبار الحجز التشغيلي دفعة محصلة.
- لا يوجد مزود تحصيل/محفظة خارجي حي أو فاتورة ضريبية قانونية إلا بعد اختيار مزود دفع ومراجعة محاسبية وقانونية.
- لا يتم بناء مزاد لحظي خارجي أو مشاركة بيانات التتبع الخام مع طرف ثالث.

## قرارات التصميم

### مواضع الإعلان والتشغيل

- قيم `placementId` معيارية ومحددة (`homepage_sponsored_products`، `homepage_featured_products`، `homepage_marketplace_ads`، `search_results`، `category_listing`، `storefront`).
- التحميل العام لا يعرض سوى حملة `approved/active` ضمن تاريخها، متجر نشط، منتج نشط ومتاح فعلياً.
- يظهر وسم **إعلان ممول** منفصلاً عن المحتوى العضوي؛ ولا يعاد ترتيب النتائج العضوية نفسها بسبب الإعلان.
- الترتيب الممول قابل للتفسير: `bid + relevance + quality + store health + availability`، مع حد لكل متجر لمنع الاحتكار.

### القياس والخصوصية

- لا يخزن النظام IP أو معرف المتصفح الخام؛ يخزن Hash أحادي الاتجاه فقط.
- `event_key` فريد وحتمي، وPostgreSQL advisory locks تحمي من التكرار وتجاوز الميزانية المتزامن.
- impression لا يسجل قبل ظهور 50% من العنصر، مع frequency cap يومي، ويحافظ الخادم على الحد حتى لو تعطلت تخزينات المتصفح.
- attribution من النقرة إلى الطلب يتم بواسطة token قصير المدة ومتحقق منه خادمياً، ولا يمنع إتمام checkout عند فشله.

### المال والفوترة

- `ad_budget_reservations` هو **حجز تشغيلي للحد المسموح صرفه**، وليس حساب أموال أو إثبات تحصيل.
- `ad_billing` هو دفتر أحداث مفوتر idempotent مرتبط بـ `event_key`؛ الحالة تنتقل من `accrued` إلى `invoiced` ثم `paid/void` فقط بسجل واضح.
- `ad_invoices` و`ad_invoice_lines` تسند رسوم اليوم السابق في فاتورة قابلة للمراجعة. لن تُعلَم كـ`paid` تلقائياً.
- CPC: تُرسمل تكلفة النقرات النظيفة؛ CPM: تُرسمل تكلفة الظهور (`bid / 1000`) مع حد أدنى يمنع دقة كسور غير مدعومة.

## أثر التوسع Scalability

| المجال | القرار |
|---|---|
| قاعدة البيانات | مفاتيح فريدة للأحداث والفواتير، وفهارس campaign/store/time/placement/status؛ لا توجد scans لنصوص خام في المسار العام. |
| مسار العرض | تحميل قائمة مرشحين محدودة ثم تصفية/ترتيب في الذاكرة؛ لا توجد استعلامات N+1 لكل بطاقة. حد العرض لكل متجر. |
| مسار الأحداث | قفل transaction لكل حملة عند حدث قابل للفوترة، لتجنب تجاوز سقف الحملة. لا يحجز قفلاً عالمياً. |
| بيانات القياس | `ad_reports` materialized يومياً؛ الصفحات الحية تعتمد على بيانات محدودة والتقارير الدورية تمنع إعادة مسح الأحداث الخام للمستخدمين. |
| Cron | pacing/reporting/invoicing يعالج على دفعات محددة ويظل idempotent عبر `source_key`، ويمكن إعادة تشغيله بأمان. |
| الكاش | cache الصفحة الرئيسية يبطل فقط عند تغيير حالة الحملة/البنر أو الإيقاف المالي؛ أحداث القياس لا تبطل الصفحة. |

## خطة الصيانة والمراقبة

- **المالك التشغيلي:** فريق المالية/الإعلانات داخل لوحة الأدمن، مع صلاحيات منفصلة للعرض والإصدار والتسوية.
- **السجلات:** audit لكل اعتماد حملة، تغيير حالة، إنشاء فاتورة وتسوية؛ correlation ID الخاص بالطلب محفوظ في طبقة التدقيق.
- **المراقبة:** cron pacing يعيد materialize التقارير وينشئ ملخصاً؛ الفشل يعاد عبر منصة cron/المراقبة القائمة. يجب تنبيه فريق التشغيل عند فشل cron أو زيادة `fraud_status=invalid`.
- **إعادة المحاولة:** إنشاء الفاتورة idempotent بواسطة `source_key` وrelations الفريدة، لذلك يمكن تشغيله مجدداً بلا ازدواجية. لا توجد محاولة تحصيل خارجية في هذه الحزمة.
- **DLQ:** لا يوجد تكامل خارجي في المسار المالي هنا؛ عند ربط مزود تحصيل مستقبلاً يجب أن يستخدم queue/DLQ مع webhook موثق، لا اتصال DB مباشر.
- **الاحتفاظ بالبيانات:** تبقى hashes وأحداث القياس وفق سياسة الاحتفاظ القانونية التي تعتمد عند الإطلاق؛ لا تستخدم كبديل لسجل الموافقة أو التحصيل.

## التوافق، الأمان والتراجع

- الإضافات schema additive فقط. تُملأ `placement_id` للحملات القديمة بقيمة متوافقة حسب النوع؛ يبقى `bid_amount` و`budget` صالحين.
- الحملات القديمة تستمر كنموذج CPC افتراضي. الحجز التشغيلي ينشأ lazy عند أول اعتماد/حدث؛ لا يُعامل تاريخياً كدفعة.
- التراجع التشغيلي: أوقف عرض placement أو أوقف الحملة؛ لا تحذف ledger/invoice. يمكن تمييز قيود الفوترة `void` بعوض تدقيقي.
- التراجع التقني: API/واجهة جديدة يمكن تعطيلها قبل تطبيق schema، وmigration لا تسقط أعمدة أو بيانات قائمة.
- الصلاحيات والفلاتر server-side؛ لا يملك التاجر عرض أو تسوية بيانات متجر آخر.

## التحقق المطلوب

- unit tests: تسعير CPC/CPM، احتياطي الميزانية، ترتيب/استبعاد المنتج، fraud policy، الفاتورة idempotency، توصية bid/budget.
- checks: lint، typecheck، tests، migration journal/Drizzle/security/diff.
- الاختبار الحي لاحقاً: PostgreSQL staging حقيقي + متصفح Playwright + cron موقّع + دورة تحصيل يدوية قبل تفعيل أي تحصيل فعلي.
