# فحص شامل لنظام العروض: التاجر → الأدمن → واجهة المتجر → الرئيسية

**التاريخ:** 2026-07-16  
**نوع العمل:** مراجعة static/code audit؛ لم يتم تعديل نظام العروض في هذه الحزمة  
**حالة البيئة:** لا توجد قاعدة بيانات Staging/Production أو تشغيل متصفح حي متاح للتحقق من رحلة فعلية

## الخلاصة التنفيذية

يوجد في المشروع أساس قوي لنظام العروض:

- صفحة التاجر: `/merchant/offers`.
- قسم عروض فعلي داخل واجهة المتجر: `StoreOffersSection`.
- مركز مراجعة الإدارة: `/admin/offers`.
- صفحة عروض عامة: `/offers` وتفاصيل العرض: `/offers/:id`.
- مواسم عروض، جدولة، تخزين مؤقت، audit log، ومخزون محجوز للباقات مع عملية تفكيك idempotent.

**لكن السلوك المطلوب غير مكتمل، ولا ينصح بإطلاق نظام العروض بوضعه الحالي.**

لا يوجد اختيار صريح للتاجر بين:

1. **نشر في نافذة عروض متجره** بصورة مباشرة.
2. **طلب نشر في الرئيسية/منصة العروض** مع رسالة واضحة بأنه ينتظر مراجعة الإدارة.

حالياً كل عرض جديد ينشأ `pending_review`، بينما يستطيع التاجر لاحقاً عبر API والواجهة تحويل العرض بنفسه إلى `approved` («نشر مباشر»). كما أن سعر العرض الظاهر للعميل لا يثبت في الطلب النهائي؛ يتم استبداله بسعر المتغير الأصلي عند مزامنة السلة. هذه فجوة حرجة تجارية وثقة عميل.

## جواب مباشر على المطلوب

| السؤال | النتيجة |
|---|---|
| هل توجد نافذة عروض في لوحة التاجر؟ | **نعم**، في `/merchant/offers` مع إنشاء باقات/خصومات وتصفية وحالة العرض. |
| هل توجد نافذة عروض داخل متجر التاجر للعميل؟ | **نعم**، `StoreOffersSection` داخل واجهة المتجر. |
| هل اختيار «نافذة متجري» ينشر مباشرة؟ | **لا**. لا يوجد هذا الاختيار؛ الإنشاء يضع كل العروض في `pending_review` وقسم المتجر لا يعرض إلا `approved`. |
| هل اختيار «الرئيسية» يرسل للمراجعة ويعرض رسالة إجراءات؟ | **لا**. لا يوجد حقل وجهة نشر أو نص إجراءات مراجعة مخصص للرئيسية. |
| هل توجد مراجعة أدمن؟ | **نعم**، قبول/رفض/إيقاف/جدولة موجودة، لكن لا تفرق بين نشر داخل المتجر ونشر في الرئيسية. |
| هل تظهر عروض معتمدة في واجهة العروض العامة؟ | **نعم**، في `/offers` عند تحقق الحالة والنافذة الزمنية والجدولة. |
| هل تظهر العروض كبطاقات مستقلة في الصفحة الرئيسية؟ | **ليس بصورة مضمونة**. قسم العروض الموسمية في الرئيسية يعرض نافذة/CTA إلى `/offers` أكثر من كونه بطاقات عروض؛ ولا يوجد ربط وجهة نشر من العرض نفسه إلى موضع رئيسية محدد. |

## تدفق النظام الحالي

```text
التاجر ينشئ عرضاً
  → status = pending_review دائماً
  → قد يحجز مخزون الباقة فوراً إن أدخل bundleQuantity
  → الأدمن يقبل/يرفض/يعطل/يجدول
  → status = approved
  → يظهر العرض في واجهة المتجر + صفحة /offers + بيانات عروض الرئيسية
```

المشكلة: `approved` حالياً يعني عملياً كل مسارات الظهور معاً، ولا توجد دلالة على أن النشر خاص بواجهة المتجر أو متاح للرئيسية فقط. كما تتيح واجهة/API التاجر طلب تغيير الحالة إلى `approved` مباشرة.

## نقاط القوة الموجودة

### التاجر

- إنشاء عروض منتج واحد، باقة، تخفيض، حصري، تصريف وموسمي.
- مراجعة حسابية قبل الإرسال في الواجهة.
- اقتراح AI محلي/مقيد مع مراجعة بشرية.
- اختيار كميات الباقة، وسعر ثابت أو نسبة خصم أو سعر لكل سطر.
- عرض قائمة بالعروض وحالاتها وملاحظات الإدارة.
- تفكيك الباقات مع idempotency وإعادة مخزون مسجلة.

### الأدمن

- مواسم/حملات عروض.
- مراجعة عروض التجار وقبولها أو رفضها أو تعطيلها أو جدولة ظهورها.
- عروض ترويجية مستقلة من الإدارة وليست سلة شراء.
- audit log وإشعار للتاجر بعد تغيير الحالة.
- قواعد ظهور رئيسية عامة وحدود للعرض لكل متجر.

### الواجهة العامة

- صفحة `/offers` ببطاقات وتفاصيل وSEO وJSON-LD.
- عروض الإدارة مع وسائل تواصل منفصلة عن عروض منتجات التجار.
- cache tags وإبطال cache عند معظم تغييرات العرض.
- قسم عروض ضمن صفحة المتجر.

## الفجوات والمخاطر مرتبة بالأولوية

## P0 — يجب علاجها قبل اعتماد النشر

### 1) لا يوجد نموذج «وجهة النشر» المطلوب

لا يوجد حقل محفوظ يفرق بين:

```text
storefront_only
homepage_review
```

الحقول الحالية `status` و`isPromoted` و`campaignId` لا تصلح بديلاً آمنًا؛ فهي تختلط بين حالة المحتوى والتمييز التجاري والمناسبة.

**الأثر:** لا يمكن تطبيق القاعدة: «المتجر فوري، الرئيسية بعد مراجعة» بصورة موثوقة.

### 2) التاجر يستطيع تجاوز مراجعة الأدمن

`PATCH /api/merchant/offers/:id` يقبل `status=approved`، وواجهة التاجر تعرض زر «نشر مباشر» للحالات `draft` أو `disabled`.

**الأثر:** يمكن نشر عرض عام/رئيسي دون موافقة الإدارة إذا كان العرض قابلًا للظهور وفق الاستعلامات الحالية. هذا يناقض سياسة المراجعة المطلوبة.

### 3) سعر العرض لا يصل إلى الطلب النهائي

صفحة تفاصيل العرض تضيف منتجات العرض إلى `localStorage` بسعر العرض. عند فتح checkout:

```text
localStorage
→ POST /api/cart
→ السعر يعاد من product_variants.price
→ POST /api/orders
→ السعر النهائي يعاد من product_variants.price
```

ولا يحمل `cart` أو `order` مرجع العرض أو سعر العرض الخادمي.

**الأثر:** العميل قد يرى سعراً مخفضاً ثم ينتقل للـ checkout بسعر المنتج الأصلي، أو يدفع السعر الأصلي. هذه أعلى فجوة ثقة وتجارية في المراجعة.

### 4) دورة مخزون الباقات غير مكتملة

- المخزون يحجز عند إنشاء عرض pending إذا وُجد `bundleQuantity`، قبل موافقة الإدارة.
- الرفض أو التعطيل أو الحذف لا يفك الحجز تلقائياً.
- حذف العرض لا يعيد المخزون.
- تعديل عناصر الباقة أو كميتها لا يسوي الحجز السابق.
- إنشاء order من العرض لا يخفض `bundleRemainingQuantity` ولا يرتبط بمرجع العرض.

**الأثر:** مخزون محجوز قد يظل عالقاً، أو يختلف المخزون المتاح عن الباقات المتبقية.

### 5) وجـهة المتجر لا تطبق visibility schedule كاملة

صفحة المتجر تتحقق من الفترة `startsAt/endsAt` وحالة `approved`، لكنها لا تمرر عروض المتجر عبر `filterVisibleBySchedule`. في المقابل صفحة تفاصيل العرض والصفحة العامة تطبقان الجدولة.

**الأثر:** قد تظهر بطاقة عرض في المتجر ثم تفتح إلى نتيجة غير متاحة بسبب جدول الظهور.

## P1 — مهم قبل التوسع التشغيلي

### 6) لا يوجد state machine موحد للعروض

هناك strings موزعة مثل `draft`, `pending_review`, `approved`, `rejected`, `disabled`، وعدة APIs تعدلها مباشرة. لا توجد سياسة انتقالات واحدة تحدد من يحق له تنفيذ كل انتقال، ومتى يعاد العرض إلى المراجعة بعد تعديل مؤثر.

### 7) `isPromoted` في نموذج التاجر خلط بين «حصري» و«ممّول»

الخانة تسمح للتاجر بتمييز عرضه، بينما ترتيب الرئيسية يعطي العروض المميزة أولوية. التمييز/التمويل يجب أن يبقى قرار أدمن أو نتيجة مسار طلب الظهور التجاري الموجود مع checkpoint مالي مستقل، وليس إدخالاً حراً من التاجر.

### 8) غياب تحقق أصناف العرض المناسب

عند الإنشاء:

- لا يتحقق المسار بشكل واضح من أن جميع `productId` موجودة؛ قد تتحول الحالة إلى خطأ داخلي بدلاً من 422.
- لا يفرض أن المنتج نشط أو أن المتغير المطلوب صالح/نشط أو أن الصنف ليس `SHOWCASE_ONLY`.
- واجهة التاجر لا تختار متغيراً محدداً للمنتج المتعدد؛ الخادم يأخذ أول متغير متاح، وقد يختلف سعره أو مخزونه عن المعروض في الواجهة.
- لا يوجد فحص مركزي أن سعر العرض أقل من السعر المرجعي أو أن سبب عدم التخفيض مبرر.

### 9) المواسم والحملات غير مكتملة إدارةً

توجد إضافة وحالة حملة، لكن لا توجد واجهة/API تعديل أو حذف واضحة لحملات العروض. كذلك لا يوجد فحص موحد أن حملة التاجر نشطة وضمن نافذتها قبل ربط العرض بها.

### 10) «الرئيسية» ليست placement محدداً من العرض

بيانات الرئيسية الحالية تستخدم عروضاً معتمدة وفق قواعد عامة، وقسم العروض الموسمية يقدم CTA إلى `/offers`. لا يوجد:

```text
offer → homepage placement → review → schedule → approved delivery
```

ولا بطاقة عرض رئيسية مضمونة مرتبطة بالعرض المختار. مسار `home-exposure` الحالي يمكن أن يكون أساساً للظهور المدفوع، لكنه ليس موصولاً بقرار العرض في نموذج التاجر.

## P2 — قابلية التوسع والصيانة وتجربة الاستخدام

1. API التاجر `GET /api/merchant/offers` يعيد كل عروض المتجر بلا pagination، بينما صفحة SSR تحدها بـ50.
2. مركز الأدمن يحمّل عدداً ثابتاً من العروض بلا بحث/فلترة/صفحات أو queue تخصصي بحسب نوع وجهة النشر.
3. اختيار منتجات العرض يعمل على أول 1000 منتج وبحث على العميل؛ يحتاج endpoint بحث paginated للمخازن الكبيرة.
4. الفهارس الحالية منفصلة غالباً (`store`, `status`)؛ الاستعلامات العامة المتكررة تحتاج فهرساً مركباً مدروساً لحالة العرض ووجهته والنافذة الزمنية.
5. لا توجد مؤشرات تشغيلية مخصصة: زمن انتظار مراجعة الرئيسية، عروض رُفضت، حجوزات مخزون عالقة، أو فرق سعر العرض/سعر الطلب.
6. لا يوجد runbook لتعطل invalidation أو لحالات الباقة العالقة.
7. لا توجد اختبارات end-to-end لدورة عرض كاملة؛ الموجود يختبر حسابات تفكيك الباقة فقط.

## التصميم الموصى به لتحقيق طلبك

## أ) نموذج نشر صريح

يضاف مجالان منفصلان:

```text
publication_target:
  storefront
  homepage

publication_state:
  draft
  storefront_live
  homepage_review
  homepage_approved
  rejected
  paused
  expired
```

ولا يستخدم `isPromoted` لتقرير وجهة النشر.

| اختيار التاجر | النتيجة | من يغيره؟ |
|---|---|---|
| نافذة عروض متجري | بعد تحقق خادمي من الأصناف والسعر والوقت يصبح `storefront_live` فوراً؛ يظهر داخل متجره فقط | التاجر ضمن حدود المتجر، والأدمن يستطيع الإيقاف |
| الرئيسية / منصة العروض | يصبح `homepage_review` | الأدمن فقط يقبل أو يرفض أو يجدول |
| بعد قبول الأدمن | `homepage_approved`، ويظهر في مواضع رئيسية مصرح بها وفي `/offers` | الأدمن |

بعد تعديل مؤثر في السعر أو العناصر أو الوقت لعرض `homepage_approved`، يعاد تلقائياً إلى `homepage_review` ولا يبقى منشوراً بقرار سابق.

## ب) رسالة واضحة للتاجر

في نموذج الإنشاء، قبل «إرسال العرض» تظهر بطاقتا اختيار:

- **نشر في نافذة عروض متجري**
  - «سيظهر العرض في صفحة متجرك بعد التحقق من الأسعار والمخزون. لا يظهر في الرئيسية أو منصة العروض العامة.»

- **طلب نشر في الرئيسية ومنصة العروض**
  - «سيتم حفظ العرض كطلب مراجعة. تراجع الإدارة السعر، الأصناف، الصور، الفترة ومكان الظهور. لن يظهر للعامة قبل الاعتماد.»

وتظهر في الجدول حالة عربية مفهومة وسبب الرفض، لا codes داخلية فقط.

## ج) تسعير العرض في السلة والطلب

لا يعتمد على `localStorage` كسعر مصدر للحقيقة. يلزم:

1. إضافة `offerId` أو `offerItemId` إلى عنصر السلة/طلب الشراء.
2. عند `POST /api/cart` و`POST /api/orders` يتحقق الخادم من:
   - حالة العرض ووجهته وفترة ظهوره وجدول الظهور.
   - ملكية المنتج/المتغير للعرض.
   - الكمية المسموحة وتركيبة الباقة.
   - `SHOWCASE_ONLY`.
3. يلتقط السعر النهائي من `store_offer_items.offer_price` داخل transaction الطلب ويخزنه snapshot في order line.
4. يظهر للعميل breakdown صريح: سعر أصلي، خصم العرض، الإجمالي.

## د) سياسة الباقات والمخزون

يجب اختيار أحد نمطين بصورة صريحة لكل عرض:

1. **Pricing-only**: لا يحجز مخزوناً عند إنشاء العرض؛ يتحقق المخزون عند checkout فقط.
2. **Allocated bundle**: يحجز المخزون فقط عند `storefront_live` أو `homepage_approved`، ويفك الحجز تلقائياً عند رفض/تعطيل/حذف/انتهاء/تعديل العرض، ويستهلك باقة واحدة بشكل ذري عند order ناجح.

أي تعديل لعناصر الباقة أو كميتها يمر عبر عملية reconcile مدققة، لا تحديث عام للصفوف.

## هـ) الرئيسية والإعلانات

- الظهور العضوي في الرئيسية بعد المراجعة ليس إعلاناً مدفوعاً ولا ينشئ فاتورة.
- الظهور الممول يستخدم مسار `home-exposure request` وcheckpoint المالي الموجود، ويحتاج قرار أدمن منفصل؛ لا يضع التاجر `isPromoted=true` بنفسه.
- يضاف renderer واضح لبطاقات العروض المعتمدة في placement رئيسي، مع badge «إعلان ممول» فقط عندما تكون الحملة مدفوعة.
- يخضع كل placement إلى cap لكل متجر، rotation وجدول `Asia/Aden` الموجودين في بنية home exposure.

## و) الأمن والصلاحيات

- يستبدل PATCH العام للعروض بأوامر نطاق محددة:

```text
merchant: save_draft | publish_storefront | request_homepage_review | pause_storefront
admin: approve_homepage | reject_homepage | pause_any | schedule_homepage
```

- يمنع التاجر من إرسال `approved`, `isPromoted`, `reviewedBy`, أو أي placement إداري.
- الرفض يحتاج سبباً واضحاً، وتعديلات الأدمن والتاجر تسجل في audit.

## ترتيب التنفيذ المقترح

### المرحلة 0 — إيقاف المخاطر الآن

1. إزالة/تعطيل انتقال التاجر إلى `approved`.
2. منع `isPromoted` من نموذج التاجر.
3. منع حذف/رفض/تعطيل باقة محجوزة قبل تفكيكها الذري أو تنفيذ release تلقائي.
4. إخفاء شراء العرض أو وسمه «قيد الإصلاح» إلى أن يصل سعر العرض للـ order الخادمي.

### المرحلة 1 — وجهة النشر والنطاق

1. Migration للوجهة والحالة/طلبات المراجعة وسبب الرفض وسجل التحولات.
2. اختيار وجهة النشر في واجهة التاجر ورسالة المراجعة.
3. queue أدمن مفصولة: عرض متجر مباشر مقابل طلب ظهور رئيسية.
4. تعديل استعلامات المتجر و`/offers` والرئيسية لتفصل الوجهات.

### المرحلة 2 — تسعير ومخزون صحيحان

1. offer-aware cart/order lines.
2. transaction حجز/استهلاك/تفكيك ومهام انتهاء العرض مع retry + DLQ.
3. reconciliation job وrunbook للعروض المحجوزة العالقة.

### المرحلة 3 — تشغيل ومراقبة

1. pagination/search للأدمن والتاجر.
2. مؤشرات: review SLA، rejected reason، conversion، stock held، price mismatch.
3. اختبارات DB integration وPlaywright لمسارات: متجر مباشر، طلب رئيسية، رفض، اعتماد، checkout، انتهاء، تفكيك وحذف.

## اختبارات إلزامية قبل النشر

- لا يمكن للتاجر نشر هدف `homepage` مباشرة عبر UI أو API.
- عرض `storefront` الحي يظهر داخل متجره ولا يظهر في `/offers` أو الرئيسية.
- عرض `homepage_review` لا يظهر في أي واجهة عامة.
- `homepage_approved` يظهر فقط في placements التي اعتمدها الأدمن والجدول الصحيح.
- سعر order line يطابق `offer_item` لا `product_variant` عندما يشتري العميل من العرض.
- رفض/حذف/انتهاء باقة يعيد المخزون مرة واحدة فقط مع idempotency.
- تعديل عرض معتمد يعيده للمراجعة ولا يترك المحتوى القديم ظاهراً.
- أصناف `SHOWCASE_ONLY` لا تدخل في مسار شراء عرض.

## حدود الفحص
