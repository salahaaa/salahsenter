# تقرير تنفيذ: دورة مالية مستقلة لكل فرع عبر ملحق العقد

**التاريخ:** 2026-07-15  
**الحالة:** مكتمل محلياً — تضاف نتائج التحقق الكامل بعد تشغيلها.

## القرار المنفذ
لكل فرع جديد:
```text
ملحق موقع للعقد الرئيسي
+ شروط إيراد مستقلة للفرع
+ كشف منصة مستقل للفرع
```

## التغيير التشغيلي

### عند مراجعة طلب الفرع
لم يعد زر الاعتماد يفعّل الفرع أو ينشئ فاتورة فرع قديمة مباشرة. بدلاً من ذلك يختار الأدمن:
- نموذج الإيراد: إيجار شهري أو عمولة مبيعات أو هجين.
- الإيجار الشهري ونسبة العمولة.
- العملة ومدة الاستحقاق وفترة السماح.

ثم ينشئ النظام **ملحق عقد مالي للفرع** تحت العقد الرئيسي، ويصبح الفرع:
```text
awaiting_addendum_signature
```
ويبقى المتجر غير نشط.

### توقيع واعتماد الملحق
- يوقع التاجر الملحق عبر مسار توقيع الملاحق الحالي.
- ينشأ PDF أرشيفي موقّع.
- لا يستطيع الأدمن تفعيل الدورة قبل أن تكون حالة الملحق `signed` وPDF جاهزاً.
- بعد الاعتماد الإداري ينشئ النظام:
  - `merchantRevenueTerms` خاصة بمتجر الفرع؛
  - `storeRentalAgreements` متوافقة مع `consolidatedBilling=true`؛
  - تفعيل الفرع والمتجر؛
  - إشعار للتاجر بأن دورة الفرع المالية أصبحت موحدة.

### ظهور الإيراد
لأن شروط الإيراد مرتبطة بـ `storeId` الفرع، تظهر دورة الفرع في كشوف `platform-revenue` المستقلة لكل متجر، مع قابلية عرض إجمالي التاجر من الحساب نفسه. إيجار وعمولة الفرع لا يختلطان مع المتجر الرئيسي.

## منع ازدواج الفوترة
- الفروع الجديدة تستخدم `financial_mode=platform_revenue` ولا ينشئ اعتمادها `store_rent_invoices` القديمة.
- الفروع القديمة تبقى `financial_mode=legacy_branch_invoice` مع فواتيرها التاريخية.
- لم يتم تحويل فروع قديمة تلقائياً؛ تحويلها يتطلب ملحقاً موقعاً ونقطة قطع مالية مدققة في دفعة لاحقة.

## البيانات
أضيف الترحيل:
```text
0076_branch_platform_revenue_contract_addendum
```
ويضيف نمط المالية ونموذج الإيراد والعمولة وdue/grace ومراجع العقد/الملحق/RevenueTerms إلى `store_branch_profiles`.
